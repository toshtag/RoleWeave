# ADR 0020: 公開求人の URL を `/:locale/jobs/:id` とし、slug を使わない

- 状態: 採用
- 決定日: 2026-08-01

この文書は日本語版を正本とする。

## 背景

P5 Public Job Discovery and SEO は、求職者が公開求人を見る経路を扱う。

公開側の URL は、後から変える費用がとくに高い。
検索エンジンに登録され、外部から参照された URL は、変えると到達できなくなる。
リダイレクトを置いても、参照する側の表示や統計は分断される。

ADR 0001 で、利用者向けの URL は `/:locale/...` とし、
表示言語の正本を URL とすることを決めている。

ADR 0019 で、公開時の見え方を `job_postings/_public` へ定義し、
「P5 の公開ページも同じ部分テンプレートを使う」と記録した。

## 決定

- 公開側の経路は `/:locale/jobs` と `/:locale/jobs/:id` とする
- 求人を指すのは数値の ID とする。題名から作る slug は使わない
- 公開側の Controller は `Public::` 名前空間へ置き、組織側の管理画面と分ける
- 表示するのは `published` の求人だけとする
- 公開中でない求人の詳細は、存在しない求人と同じ 404 とする
- ログインを要求しない
- 詳細は `job_postings/_public` をそのまま使う
- 一覧と詳細に canonical URL を出力する
- `canonical` の宣言は、必要な画面だけが `content_for :canonical` で行う

## 理由

slug を使わないのは、日本語の題名から有用な ASCII の slug が作れないためである。
`"採用担当".parameterize` は空文字列になる。
非 ASCII をそのまま URL へ置くと、多くの文脈で percent encoding として表示され、
読みやすさの利点が失われる。
「日本語のときだけ ID、英語のときだけ slug」という分け方は、
同じ求人が言語によって別の URL になり、canonical の判断を難しくする。

数値の ID を使うことで、登録されている求人の数と範囲は推測できる。
公開されている求人については、その情報が問題になる場面がない。

`Public::` 名前空間へ分けるのは、
「ログインが要る画面」と「誰でも見られる画面」が
同じ Controller の中で分岐しないようにするためである。
分岐が増えると、公開してはいけないものが公開される経路が生まれる。

公開中でない求人を 404 にするのは、403 と分けると
審査中の求人があることだけが分かるためである。
求人の ID を順に試すことで、その組織がいま何件を準備しているかが推測できる。

`canonical` を必要な画面だけの宣言にするのは、
`robots` と同じ理由による（ADR 0019）。
既定で出すと、出すべきでない画面にも出る。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| `/jobs/:id-:slug` の形にする | 日本語の題名から有用な slug が作れない |
| 言語ごとに slug の有無を変える | 同じ求人が言語によって別の URL になる |
| 求人へ非連番の公開 token を持たせる | 公開求人に対して、件数を隠す必要がない |
| 公開側と管理側を同じ Controller にする | 公開してはいけないものが公開される経路が生まれる |
| 公開中でない求人へ 403 を返す | 審査中の求人があることだけが分かる |
| すべての画面へ canonical を出す | 出すべきでない画面にも出る |

## 影響

- 求人の URL は `/:locale/jobs/:id` で確定する。以後この形を変えない
- 組織を URL で指す識別子はまだない。組織の公開ページを作るときに決める
- 一覧の絞り込みと並び替えは、この ADR では扱わない（P5-T2 以降）。
  絞り込みを query string で表す場合、canonical をどう出すかを合わせて決める
- ページネーションもまだない。`page` を持つ URL の canonical は P5-T3 で決める
- 求人の閲覧数は記録していない
