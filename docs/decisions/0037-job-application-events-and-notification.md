# ADR 0037: 応募の記録を別の表に残し、通知はトランザクションの外で積む

- 状態: 採用
- 決定日: 2026-08-02

この文書は日本語版を正本とする。

## 背景

P7 の完了条件は「通知の失敗で応募が巻き戻らない」を含む。
対象範囲は「応募イベント」「応募後の非同期通知」を含む。

ADR 0034 で、プロフィールを削除すると応募も消えると決めた。
そのとき「企業側に残す記録は応募イベントが持つ」と記録している。
その記録がなければ、応募があったこと自体が消える。

組織の所属の変更（ADR 0014）と求人の状態の変更（ADR 0018）は、
同じ理由で記録を別の表に残している。

通知はアプリケーションの外（SMTP）へ出る。
こちらの都合では成功を保証できない。

## 決定

- 応募イベント（`job_application_events`）を追加する。記録するのは「応募」と「取消」
- 対象の応募・求人が消えても記録は残す。参照は nullify する
- **求人の題名と応募者の表示名を、記録の中に写して持つ**
- 記録の内容は後から書き換えられない（`attr_readonly`）
- 記録はモデル（`after_create` / 状態の変更）で書く
- **通知は `after_commit` で `deliver_later` する**
- 宛先は、その組織の**管理者**とする。一般の所属者へは送らない
- 取消では通知しない
- **メールの本文に応募者の経歴を書かない。**届いたことと、見に行く経路だけを伝える

## 理由

記録を別の表に残すのは、応募そのものが消えうるためである。
求職者がプロフィールを消せば応募も消える。
企業側から見ると、選考していた相手が痕跡なく消えることになる。

題名と表示名を写して持つのは、参照が消えた後でも
「何の応募だったか」を読めるようにするためである。
`job_posting_id` だけを持っていても、求人が消えれば空欄の履歴になる。

記録をモデルで書くのは、応募を作る経路が増えても書き忘れが起こらないようにするためである。
所属（ADR 0014）と求人（ADR 0018）でも同じ形にしている。

通知を `after_commit` で積むのは、**通知の失敗で応募が巻き戻らない**ようにするためである。
同じトランザクションの中で送ると、SMTP が落ちているだけで応募が失敗する。
応募は求職者にとって取り返しのつきにくい操作であり、
「送信できなかったのでなかったことにする」は成り立たない。

`deliver_later` にするのは、送信の待ち時間を応募の応答に載せないためである。
外部のサーバーが遅い場合、その分だけ利用者が待つことになる。

宛先を管理者に限るのは、応募が届いたことが組織の運営に関わる情報であるためである。
所属者全員へ送ると、関係のない人にも応募の発生が伝わる。

取消で通知しないのは、取消が急を要さないためである。
一覧と記録に残るため、次に見たときに分かる。

本文に経歴を書かないのは、メールが転送も保存もされる経路であるためである。
公開範囲（ADR 0030）の設定が効かない場所へ個人情報を写すことになる。
本文に書けば、公開範囲を閉じた後も、その内容は受信箱に残り続ける。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| 記録を持たず、応募の行だけで足りるとする | プロフィールの削除で、応募があったこと自体が消える |
| 記録に id だけを持つ | 参照が消えると、空欄の履歴になる |
| 記録を Controller で書く | 応募を作る経路が増えたときに書き忘れる |
| 通知を同じトランザクションで送る | メールが送れないだけで応募が失敗する |
| 通知を `deliver_now` にする | 送信の待ち時間が応募の応答に載る |
| 所属者全員へ通知する | 関係のない人にも応募の発生が伝わる |
| 本文に応募者の経歴を書く | 公開範囲を閉じた後も、その内容が受信箱に残り続ける |
| 取消も通知する | 急を要さない。一覧と記録に残る |

## 影響

- 通知の失敗は、いまのところ記録されない。
  積んだ後の失敗（再試行の枯渇）を可視化するのは P11 で扱う
- 通知の受け取りを止める設定はない。P9（通知）で扱う
- 求職者への通知は送っていない。応募したことは本人が知っている
- `job_application_events` の保存期間は未定である。P10 で扱う
- 選考の状態の変更（P8）も、同じ表に足すか別の表にするかを、そのときに決める
