# ADR 0062: 逆プロキシの前提を設定として受け、書かない場合の挙動は変えない

- 状態: 採用
- 決定日: 2026-08-02

この文書は日本語版を正本とする。

## 背景

production は `config.assume_ssl = true` を置いている。
これは「前段に TLS を終端する逆プロキシが居る」という前提であり、
`X-Forwarded-Proto` を無条件に信じる設定である。

一方で、次の 2 つは設定していなかった。

- **どのプロキシを信じるか**（`config.action_dispatch.trusted_proxies`）
- **どのホスト名を受け入れるか**（`config.hosts`。生成時のコメントのまま）

`ActionDispatch::RemoteIp` は、信頼するプロキシを除いたうえで
最も外側の IP を `request.remote_ip` として返す。
信頼するプロキシを設定していないため、除かれるのは既定の範囲
（ループバックと私用の範囲）だけである。

プロキシを置かない構成、または `X-Forwarded-For` を上書きせず、
かつ前段が公開の IP を持つ構成では、
**利用者が書いた `X-Forwarded-For` がそのまま `remote_ip` になりうる。**

`remote_ip` は次の 2 か所が使う。

- レート制限（ADR 0044）。`rate_limit` は既定で `request.remote_ip` を単位に数える
- 記録。`AccessEvent` と `AuthenticationEvent` が保存する（ADR 0047、ADR 0010）

つまり、header を変えるだけで**レート制限を数え直させられ**、
**監査ログへ任意の IP を残せる**。

自己ホストの環境の設定そのものは `SECURITY.md` の対象外である。
ここで扱うのは、アプリケーション側が前提を**設定として受けられること**と、
逆プロキシに求める条件を**文書に書くこと**である。
`assume_ssl` を置きながら前提を書いていない状態は、こちら側の欠落である。

## 決定

- 信じる前段を環境変数 `TRUSTED_PROXIES`（IP または CIDR のカンマ区切り）で受ける
- 受け入れるホスト名を環境変数 `ALLOWED_HOSTS`（カンマ区切り）で受ける
- **どちらも書かない場合は、いままでと同じ挙動とする**
- 信じる前段は Rails の既定へ**足す**。既定を置き換えない
- `config.hosts` も**足す**。置き換えない
- 稼働確認の経路（`/up`）は名前の検証から除く
- IP でも CIDR でもない値は、**起動の時点で失敗する**
- 環境変数の読み方は `lib/reverse_proxy.rb` へ 1 か所で置く
- 逆プロキシに求める条件と、満たさない場合に効かなくなるものを
  `docs/operations/reverse-proxy.md` へ書く

## 理由

**書かない場合の挙動を変えない**のは、既定で拒否にすると
設定のない起動が理由の分からない失敗になるためである。
自己ホストの利用者は、まず動かしてから運用の設定を詰める。
最初の起動が「403 しか返らない」状態になると、原因を設定へ辿り着けない。

**既定へ足す**のは、置き換えるとループバックと私用の範囲が
プロキシとして扱われなくなるためである。
前段が同じホストに居る構成が壊れる。

`/up` を除くのは、監視が名前ではなく IP で叩く構成があるためである。
`ALLOWED_HOSTS` を書いた時点で稼働確認が落ちると、
設定を入れた側にはアプリケーションが壊れたように見える。

**起動の時点で失敗させる**のは、黙って読み飛ばすと
信じるつもりの前段が信じられていない状態のまま動くためである。
その状態は、レート制限が効かないことに気付けない状態でもある。

読み方を 1 か所へ置くのは、環境ごとの設定ファイルへ書くと
書式の検査が環境の数だけ増えるためである。
`lib/` へ置き、autoload の対象から外す。
環境の設定ファイルは初期化のごく早い段階で読まれ、autoload では間に合わない
（`localized_public_exceptions.rb` と同じ理由）。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| いまのまま（設定を持たない） | header を変えるだけでレート制限を回避でき、記録を汚せる |
| 既定で内部の範囲だけを信じ、外は拒否する | 設定のない起動が理由の分からない失敗になる |
| `trusted_proxies` で Rails の既定を置き換える | 前段が同じホストに居る構成が壊れる |
| `config.hosts` を書き換え（`=`）で渡す | Rails が足す既定の項目を落とす |
| `/up` も名前の検証の対象にする | 監視が IP で叩く構成で落ちる。アプリが壊れたように見える |
| 不正な値を読み飛ばす | 信じていない前段を信じたつもりのまま動く |
| 設定ファイルへ直接書かせる（環境変数を使わない） | 自己ホストごとに差分が出る。更新のたびに衝突する |
| `remote_ip` を使うのをやめる | レート制限と記録の単位がなくなる。ADR 0044 の判断を覆す |

## 影響

- 設定を書かない環境の挙動は変わらない。**この ADR だけでは何も守られない**。
  守りが働くのは、運用の側が `TRUSTED_PROXIES` を書いたときである
- 書かない場合に効かなくなるものを `docs/operations/reverse-proxy.md` へ書いた。
  脅威モデルの「受け入れているリスク」へも行を足した
- `ALLOWED_HOSTS` を書くと、書いていないホスト名での要求が 403 になる。
  名前を増やすときは設定の更新が要る
- メールのリンクのホスト名は、これとは別に
  `config.action_mailer.default_url_options` が持つ
