# ADR 0025: 公開ページを条件付き GET だけでキャッシュする

- 状態: 採用
- 決定日: 2026-08-02

この文書は日本語版を正本とする。

## 背景

P5 の対象範囲は「公開ページのキャッシュ方針」を含む。

公開求人の一覧・詳細・sitemap は、毎回すべてを組み立てて返している。
内容が変わっていなくても、同じ本文を毎回送る。

一方、共通レイアウトはログイン状態によって変わる。
ヘッダーに、未ログインなら「ログイン」、ログイン中ならメールアドレスが出る。
応答をそのまま共有キャッシュ（CDN、リバースプロキシ）へ載せると、
別の利用者のヘッダーを含む応答が配られうる。

方針を決めずに `Cache-Control` を付けると、この違いを見落とす。

## 決定

- 公開求人の一覧・詳細は、条件付き GET（`ETag` / `Last-Modified`）を有効にする
- これらの応答は共有キャッシュへ載せない（`Cache-Control: private`）
- ETag の材料に**ログイン状態**を含める
- 一覧の ETag には、絞り込みの条件と現在のページ番号も含める
- `Last-Modified` は、対象となる求人の最終更新時刻から作る
- `sitemap.xml` と `robots.txt` は共有キャッシュを許す（`public`）。
  sitemap は 1 時間、robots は 1 日の `max-age` を付ける
- `Rails.cache` によるページ・フラグメントキャッシュは使わない
- CDN、リバースプロキシの設定は行わない

## 理由

条件付き GET を選ぶのは、再描画と転送量の両方を減らせるためである。
304 を返せば本文を組み立てる必要がなく、送る必要もない。
保存する場所を持たないため、無効化の設計も要らない。

公開求人を `private` にするのは、レイアウトがログイン状態で変わるためである。
`public` にすると、ログイン中の利用者へ返した応答が
未ログインの利用者へ配られうる。
逆も起こり、ログインしているのに「ログイン」と表示される。

ETag へログイン状態を含めるのは、同じ URL でも応答が変わるためである。
含めないと、ログインの前後で 304 が返り、ヘッダーが古いままになる。

一覧の ETag へ条件とページ番号を含めるのは、
同じ URL でも query string が違えば別の応答になるためである。
Rails の `fresh_when` は URL を材料にしないため、明示的に渡す。

sitemap と robots に `public` を許すのは、
どちらもログイン状態に依存しないためである。
sitemap の `max-age` を 1 時間にするのは、
公開した求人が検索へ現れるまでの遅れを 1 時間以内に抑えるためである。

`Rails.cache` を使わないのは、保存したものを「いつ捨てるか」の設計が要るためである。
求人の更新、状態の変更、組織名の変更のそれぞれで、
どのキーを捨てるかを決めることになる。
条件付き GET であれば、`ETag` の材料が変われば自動的に別の応答になる。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| 公開求人を `public` でキャッシュする | ログイン状態で変わるヘッダーが別の利用者へ配られる |
| ETag からログイン状態を外す | ログインの前後で 304 が返り、ヘッダーが古いままになる |
| `Rails.cache` でページを保存する | 「いつ捨てるか」の設計が要る。無効化の漏れが古い内容として現れる |
| レイアウトからログイン状態を外して `public` にする | 公開ページからログイン状態が分からなくなる |
| CDN の設定をここで決める | 動かす環境が利用者ごとに違う。アプリケーション側の契約を先に固める |

## 影響

- 公開ページは共有キャッシュへ載らない。
  同時アクセスが増えた場合の負荷は、アプリケーションが受ける。
  観測は P11 Performance and Observability で行う
- 共有キャッシュを使いたい場合は、ヘッダーのログイン状態部分を
  応答から切り離す必要がある。その判断は、必要になった時点で行う
- 一覧の `Last-Modified` は、条件に一致する求人の最終更新時刻である。
  条件が変わると値も変わる
- 求人が削除された場合、一覧の ETag は残った求人から作られるため変わる。
  削除は現時点で経路がない
