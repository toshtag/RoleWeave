# ADR 0049: N+1 はテストで止め、遅い SQL は値を伏せて記録する

- 状態: 採用
- 決定日: 2026-08-02

この文書は日本語版を正本とする。

## 背景

P11 の完了条件は「N+1 と遅い SQL を検出できる」を含む。

N+1 は「動くが遅い」欠陥である。
`includes` を外しても画面は正しく表示される。**動くから気付かない。**

遅い問い合わせも同じである。
P5 から「`ILIKE '%...%'` は索引が効かない」を持ち越しているが、
実際にどれが遅いかは測っていない。

商用の監視サービスへの依存は非目標である（P11 の `non_goals`）。

## 決定

- **N+1 はテストで検出する。**件数を増やしても問い合わせの数が増えないことを確かめる
- 数える補助（`count_queries`）をテストの土台へ置く
- 対象は一覧の画面とする（公開求人、応募、やり取り、通知、
  候補者の検索、Webhook の配信先）
- **preload した関連へ scope を付けない。**並び順や絞り込みが要る場合は、
  関連の定義側（`has_many :skills, -> { alphabetical }`）へ持たせる
- 一覧が関連の 1 件だけを使う場合、関連ごと preload しない。
  必要な 1 件を 1 回の問い合わせで引く
- 問い合わせの数だけでなく、**読み込んだ行の数**も対象にする。
  数える補助（`count_loaded`）を置く
- 遅い SQL は構造化ログ（ADR 0048）として出す。水準は `warn`
- しきい値（`SlowQueryLogger::THRESHOLD_MS`）は 100 ミリ秒とし、1 か所へ置く
- **値（bind）を出さない**
- 接続の維持や暗黙の問い合わせ（`SCHEMA` / `TRANSACTION` / `CACHE`）は対象にしない
- 新しい依存を足さない

## 理由

N+1 をテストで止めるのは、実行時の検出では遅いためである。
本番で遅くなってから気付くのでは、利用者が先に困る。
「件数を増やしても数が変わらない」を固定すれば、`includes` を外した変更がその場で落ちる。

一覧を対象にするのは、N+1 が件数とともに現れるためである。
詳細の画面は 1 件しか扱わない。

preload した関連へ scope を付けないのは、**それが読み直しになる**ためである。

```ruby
# Controller
scope = CandidateProfile.searchable.includes(:skills)
```
```erb
<%# View: 読み込み済みの関連へ scope を付けると、新しい relation ができて SQL が飛ぶ %>
<%= candidate_profile.skills.alphabetical.map(&:name).join(" / ") %>
```

`includes` が書いてあるため、**コードを読むだけでは N+1 に見えない。**
preload は行われ、その結果は捨てられ、そのうえで件数分の問い合わせが飛ぶ。
最初の実装で 2 か所（候補者の検索のスキル、Webhook の配信の記録）がこの形だった。

並び順を関連の定義側へ置けば、preload した結果がそのまま並ぶ。
読み出す側は scope を書く必要がなく、書けなくなる。

関連の 1 件だけを使う場合に preload しないのは、
preload が「全件」しか読めないためである。
Webhook の一覧は配信先ごとの最新の 1 件を出すが、
`includes(:webhook_deliveries)` はその配信先のすべての記録を読む。
配信の記録は保持期限の対象外であり（ADR 0046）、増え続ける。

読み込んだ行の数も見るのは、**問い合わせの数では検出できない**ためである。
preload は 1 回であり、その 1 回が 10 行を読むか 100 万行を読むかは、
問い合わせの数に現れない。`instantiation.active_record` の `record_count` で数える。

遅い SQL を実行時に記録するのは、遅さが環境で変わるためである。
テストのデータ量では、どの問い合わせも速い。
実際の件数と実際のハードウェアで測るしかない。

値を出さないのは、構造化ログと同じ理由による（ADR 0048）。
`WHERE email_address = 'member@example.com'` がそのまま残る形は避ける。
Rails は既定で bind を SQL の文字列へ埋めないため、
`payload[:sql]` を出す限り値は含まれない。テストでそれを固定した。

しきい値を 100 ミリ秒にしたのは、画面の応答として気になり始める水準だからである。
**値そのものに根拠はない。**測った結果に応じて見直す。
その前提を ADR に書いておかないと、根拠のある値として扱われる。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| N+1 を実行時にだけ検出する | 本番で遅くなってから気付く |
| `bullet` などの gem を入れる | 依存が増える。標準の通知で足りる |
| 全画面の N+1 を網羅する | 件数とともに現れるのは一覧である。詳細は 1 件しか扱わない |
| 遅い SQL をテストで検出する | テストのデータ量では、どの問い合わせも速い |
| SQL の値を出す | 個人情報がログへ残る |
| しきい値を根拠のある値として書く | 測っていない値に根拠はない。見直す前提を明示する |
| 商用の APM を入れる | 非目標である |
| 並び順を読み出す側（View）へ書く | preload した結果を捨てて引き直す。`includes` があるため N+1 に見えない |
| 関連の 1 件を preload で取る | preload は全件しか読めない。増え続ける関連ではメモリを使い切る |

## 影響

- しきい値は環境ごとに変えられない（定数である）。
  必要になった時点で設定へ移す
- 遅い SQL の記録は、遅い環境ではログが増える。
  出力先の運用に委ねる
- 一覧の N+1 のテストは、対象の画面を足すたびに書く必要がある。
  自動では網羅されない
- 関連の定義へ並び順を持たせると、その関連を使うすべての経路の並びが決まる。
  別の並びが要る経路は、そこで明示的に order を書くことになる
- N+1 のテストは、**何を増やすかで結果が変わる**。
  応募の記録の変更者は、変更者を持たない記録を増やしても検出できない
  （`belongs_to` は外部キーが nil なら問い合わせない）。
  テストが増やすものが、実際に画面へ出るものと同じかを確かめる
- `ILIKE '%...%'` の全件走査は、この仕組みで**測れるようになっただけ**である。
  索引の追加は、測った結果に基づいて別に判断する
