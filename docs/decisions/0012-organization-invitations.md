# ADR 0012: 組織への招待をメールアドレス宛の署名付き token で行う

- 状態: 採用
- 決定日: 2026-08-01

この文書は日本語版を正本とする。

## 背景

ADR 0011 で、組織と所属を分けて持つことを決めた。
現時点で組織に入れるのは、その組織を作成したアカウントだけである。

P3 の完了条件は「組織を作成しメンバーを招待できる」を含む。

招待には、他の token と違う制約がある。
招待した時点で、相手のアカウントがまだ存在しないことがある。
採用の担当者は、同僚のメールアドレスを知っていても、
その人がこのサービスへ登録しているかは知らない。

## 決定

- 招待（`invitations`）は、組織・宛先のメールアドレス・役割・招待した人を持つ
- 宛先はメールアドレスとする。アカウントへは結び付けない
- 受諾リンクの token は `generates_token_for` で作り、token を保存しない
- token へ宛先のメールアドレスと受諾時刻を含める
- 有効期限は 7 日とする
- 招待を作れるのは、その組織に所属するアカウントだけとする
- 受諾できるのは、招待された宛先と同じメールアドレスでログインしている場合だけとする
- 未ログインで受諾のリンクをたどったら、ログイン後にそのリンクへ戻す
- すでにその組織の所属がある場合は、所属を増やさずに受諾を成功として扱う
- 未受諾の招待は、同じ組織・同じ宛先で 1 件までとする。受諾済みは対象にしない
- 受諾の失敗理由（壊れている、期限切れ、宛先の変更後、受諾済み）を画面で区別しない
- 招待した人のアカウントが削除されても、招待の事実は残す

## 理由

宛先をメールアドレスにするのは、招待した時点で相手のアカウントが
存在しないことがあるためである。
アカウントへ結び付けると、その状態を表せない。
「先にアカウントを作らせてから招待する」順序を強いると、
招待する側が相手の登録状況を調べる必要が出る。

token へ受諾時刻を含めるのは、受諾した時点で発行済みのリンクを
無効にするためである。使い切りの印を別に持たなくてよい。
印を持つ方式では、印を消す処理が失敗したときに token が生き残る。

token へ宛先を含めるのは、宛先を変えた後に古いリンクが通ると、
確かめていない相手が組織へ入れるためである。

有効期限を 7 日にするのは、短すぎると気付く前に切れ、
長すぎると転送されたメールがいつまでも使えるためである。
確認リンク（24 時間）より長くしているのは、
招待が相手の都合で放置されうるものであり、
本人がすぐに操作するとは限らないためである。

受諾に宛先の一致を求めるのは、リンクを手にした別人が組織へ入れないようにするためである。
メールは転送される。リンクだけで入れる設計にすると、
転送先の人がそのまま組織のデータへ到達する。

すでに所属がある場合を成功にするのは、
「受諾できなかった」と伝えると、すでに入れている利用者を混乱させるためである。

未受諾を 1 件までにするのは、同じ相手へ何通も届く状態を避けるためである。
受諾済みを対象にしないのは、同じ人が組織を抜けた後に招待し直せる必要があるためである。

招待した人が削除されても招待を残すのは、
「誰が招待したか」が失われても「招待があった」事実は調査に要るためである。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| 招待をアカウントへ結び付ける | 招待した時点で相手のアカウントが存在しないことがある |
| token をデータベースへ保存する | 漏えいした時点でそのまま使える文字列が残る |
| 受諾に宛先の一致を求めない | 転送されたリンクで別人が組織へ入れる |
| すでに所属がある受諾を失敗にする | すでに入れている利用者を混乱させる |
| 未受諾でも同じ宛先へ何件でも作れる | 同じ相手へ何通も届く |
| 受諾済みも含めて 1 件までにする | 一度抜けた人を招待し直せない |
| 招待から直接アカウントを作る | 招待の経路とアカウント作成の経路が二重になる |

## 影響

- 招待を作れるのは「その組織の所属」であり、役割は問わない。
  役割による制限は P3-T3 で決める
- 招待の取り消し、再送、一覧の画面はない。別のタスクで扱う
- 組織のメンバー一覧の画面はない。別のタスクで扱う
- アカウントを持たない相手を招待した場合、その人は先にアカウントを作る必要がある。
  招待メールからアカウント作成へ直接つなぐ導線はまだない
- 招待の作成に回数の制限がない。同じ組織から多数の宛先へ送れる状態が残る
