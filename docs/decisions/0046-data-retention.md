# ADR 0046: 保持期限を表ごとに決め、消し方を削除と匿名化に分ける

- 状態: 採用
- 決定日: 2026-08-02

この文書は日本語版を正本とする。

## 背景

P10 の完了条件は「保持期限を過ぎたデータを削除または匿名化できる」を含む。

これまでのフェーズで、保持期限を「P10 で扱う」として先送りしてきた。
認証の記録（ADR 0010）、権限の変更（ADR 0014）、公開状態（ADR 0018）、
応募の記録（ADR 0037）、評価（ADR 0039）、面接の予定（ADR 0040）、
メッセージ（ADR 0041）、通知（ADR 0042、0043）である。

期限を決めないと、個人情報を含む記録が無期限に残る。
一方、記録には残す理由がある。監査と選考の経緯である。

## 決定

- 保持の方針を `DataRetention` の 1 か所へ置く
- 表ごとに「期間」と「消し方」を決める。消し方は `:delete` と `:anonymize` の 2 つ
- 期限を設ける表は 3 つとする
  - `sessions`（90 日、削除）
  - `notifications`（180 日、削除）
  - `authentication_events`（1 年、**匿名化**）
- **対象にしない表は、その理由を明示する**
- 期間・除外のどちらにも入っていない表があると、**テストが落ちる**
- 実行は rake タスク（`report` と `apply`）から行う
- **自動実行はしない**
- 件数を必ず出力する

## 理由

消し方を分けるのは、記録に残す理由があるためである。
認証の記録は「いつ何が起きたか」を残す必要がある（ADR 0010）。
行ごと消すと、削除の前後の調査ができなくなる。
メールアドレスだけを置き換えれば、個人を特定できないまま経緯は残る
（ADR 0033 の匿名化と同じ扱いにそろえた）。

セッションと通知を削除するのは、残す理由がないためである。
期限の切れたセッションは再利用されない。
読んだ後の通知は、中身を元の記録が持っている。

応募・メッセージ・評価・面接の予定を期限の対象にしないのは、
選考の経緯であり、応募の削除（ADR 0034）で消えるためである。
時間で消すと、進行中の選考の途中でも消えうる。

網羅をテストで固定するのは、表が増えるためである。
「対象の一覧」だけを持つと、増えた表は黙って対象外になる。
両方を持ち、どちらにも入っていない表があれば落ちるようにすれば、
表を足した人が「どれだけ残すか」を必ず決めることになる
（エクスポートの列の扱い（ADR 0032）と同じ形である）。

自動実行しないのは、何をいつ消すかが運用の判断であるためである。
気付かないうちに消えている状態を作らない。
自己ホストの利用者が、自分の運用に合わせて呼ぶ。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| すべてを一律の期間で消す | 監査の記録と選考の経緯が失われる |
| 認証の記録を行ごと消す | 削除の前後の調査ができなくなる |
| 応募・メッセージも期限で消す | 進行中の選考の途中でも消えうる |
| 対象の一覧だけを持つ | 増えた表が黙って対象外になる |
| 自動で実行する | 気付かないうちに消えている状態を作る |
| 組織ごとに期限を設定できるようにする | 設定の数だけ、消えない理由が増える |

## 影響

- 表を足したときは `DataRetention` へ書く必要がある。テストが強制する
- 実行は運用者に委ねる。呼ばなければ、いつまでも残る
- 削除・匿名化そのものは記録に残らない。
  何件処理したかは実行時の出力にだけ現れる
- `notifications` を消すと、失敗した配信の記録（ADR 0043）も一緒に消える。
  失敗の調査は 180 日以内に行う必要がある
- 匿名化の方法は表ごとに書く必要がある。
  いまは `authentication_events` だけであり、ほかの表を足すときは方法も決める
