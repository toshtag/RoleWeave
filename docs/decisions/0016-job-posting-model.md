# ADR 0016: 求人の公開状態を 1 つのレコードで持ち、本文を項目に分ける

- 状態: 採用
- 決定日: 2026-08-01

この文書は日本語版を正本とする。

## 背景

P4 Job Posting Management は、下書き、公開申請、審査、公開、停止、公開履歴を扱う。

求人は、このサービスで最初の「組織に属する業務データ」になる。
ADR 0013 と P3-T4 で、組織へ従属するモデルの契約
（所属先を作成後に変更できない、組織を必須とする、組織の削除で消える）を
構造として固定した。求人はその最初の適用先になる。

公開状態の持ち方は、後から変える費用が高い。
下書きと公開を別のレコードにするか、1 つのレコードの状態にするかで、
申請・審査・停止・履歴のすべての設計が変わる。

## 決定

- 求人（`job_postings`）は組織へ従属する
- 公開状態は 1 つのレコードが `status` として持つ。下書きと公開でレコードを分けない
- 状態の値は `JobPosting::STATUSES` へ閉じる。`draft` から始める
- 本文は項目に分ける
  （題名・仕事内容・勤務地・職種・雇用形態・給与・応募条件）
- 雇用形態は `JobPosting::EMPLOYMENT_TYPES` へ閉じる。自由記述にしない
- 状態は画面のフォームから受け取らない。公開状態を変える経路は別に用意する
- 求人を作成・編集できるのは、その組織の所属であれば役割を問わない

## 理由

公開状態を 1 つのレコードで持つのは、下書きと公開を別レコードにすると
「どちらが正か」を扱う場所が増えるためである。
別レコードにする方式は、公開中の求人を編集しながら公開内容を保つ用途では有利だが、
その用途はまだない。必要になった時点で、公開版のスナップショットを足す方が、
最初から二重に持つより費用が小さい。

状態の値を閉じるのは、自由な文字列を許すと
「公開中とは何か」を判断する場所が増えるためである。

状態を `draft` だけから始めるのは、制限したい遷移がまだ決まっていないためである。
使い道のない状態を先に並べても、どこで効くのかを誰も判断できない。
これは ADR 0011 で役割を 2 つから始めたのと同じ考え方による。

本文を項目に分けるのは、1 つの自由記述へまとめると
公開側の検索と表示で毎回解析することになるためである。
勤務地や雇用形態での絞り込みは P5 の対象であり、
そのときに本文から抜き出すのでは、書き方に依存した結果になる。

雇用形態を閉じるのは、公開側の絞り込みで表記のゆれを吸収しないためである。
「正社員」「正社員（試用期間あり）」「フルタイム」が別の値になると、
絞り込みが機能しない。

状態をフォームから受け取らないのは、
編集の経路がそのまま公開の経路になってしまうためである。
公開には審査を挟む。

編集できる範囲を役割で分けないのは、制限したい操作がまだ固まっていないためである。
「下書きは誰でも、公開申請は管理者だけ」のような分け方は、
申請の経路を作るタスクで判断する。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| 下書きと公開を別のレコードにする | 「どちらが正か」を扱う場所が増える。必要な用途がまだない |
| 状態を真偽値（`published`）で持つ | 申請中・停止中を表せない |
| 状態を自由な文字列にする | 「公開中とは何か」を判断する場所が増える |
| 本文を 1 つの自由記述にまとめる | 公開側の検索と表示で毎回解析することになる |
| 雇用形態を自由記述にする | 表記のゆれで絞り込みが機能しない |
| 状態をフォームから受け取る | 編集の経路がそのまま公開の経路になる |
| 編集を管理者だけに限る | 制限したい操作が固まっていない。日々の編集が滞る |

## 影響

- 状態を増やすタスク（公開申請・審査・公開・停止）は、
  `STATUSES` と遷移の規則を同時に足す
- 公開中の求人を編集したときに公開内容がすぐ変わる。
  公開版を固定したい場合は、そのときにスナップショットを足す
- 求人の削除、複製、テンプレートはまだない
- 給与は文字列である。金額での絞り込みや通貨換算はできない。
  必要になった時点で構造化する
- 勤務地は文字列である。地域での絞り込みは、P5 で正規化の要否を判断する
