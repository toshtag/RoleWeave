# ADR 0015: 運営者権限をサーバー運用者のものとし、専用の経路へ分ける

- 状態: 採用
- 決定日: 2026-08-01

この文書は日本語版を正本とする。

## 背景

ADR 0013 の「影響」に、管理者が 0 人になった組織からの復旧は
「運営者権限（P3-T6）を待つことになる」と記録した。

P3 の対象範囲は「運営者権限」を含む。

このプロジェクトは自己ホスト可能な OSS として配布する。
そのため「運営者」は、外部のサービス提供者ではなく
「そのサーバーを運用している人」である。
この違いは、権限の与え方を決める。
外部の提供者であれば画面から管理する必要があるが、
サーバーの運用者はサーバーへ入れる。

## 決定

- 運営者かどうかは `users.operator` で表す。既定は false
- 画面から運営者を付与・剥奪する経路は作らない。
  `bin/rails roleweave:operator:grant[...]` / `:revoke[...]` で行う
- 運営者の経路は `Operator::BaseController` を土台とする専用の名前空間へ置く
- 運営者ができるのは、すべての組織の一覧、組織の内容の閲覧、
  メンバーへの管理者の役割の付与の 3 つだけとする
- 運営者の操作も、通常の権限変更と同じ履歴へ記録する（主体は運営者）
- 運営者でないアカウントが運営者の経路へ入ろうとしたら 404 を返す
- 運営者は、通常の組織の画面（`organizations`、`memberships`、`invitations`）では
  何の特権も持たない

## 理由

画面から付与しないのは、自己ホストの前提では運営者がサーバーへ入れるためである。
画面を作ると、その画面自体が「運営者になるための経路」になり、
守るべき対象が 1 つ増える。
最初の運営者をどう作るかという問題も残る。

専用の名前空間へ分けるのは、組織の所属に基づく制限と運営者の権限が
同じ経路の中で絡み合うと、どちらで通ったのかが読めなくなるためである。
通常の画面へ「運営者ならば通す」を足すと、
その分岐が増えるたびに、意図しない組み合わせが生まれる。

できることを 3 つに限るのは、運営者が「組織の中身を自由に見られる人」に
ならないようにするためである。
このサービスは応募者の個人情報を扱う。
復旧に必要な範囲を超えた閲覧は、必要になった時点で個別に判断する。

404 を返すのは、403 と分けると運営者の経路が存在することだけが分かるためである。

運営者の操作を同じ履歴へ記録するのは、
「誰が復旧したか」が通常の権限変更と同じ重さを持つためである。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| 画面から運営者を付与する | その画面自体が運営者になる経路になる。最初の運営者をどう作るかも残る |
| 運営者を組織の役割として扱う | 組織に属さない権限であり、所属の表に置くと意味が二重になる |
| 通常の画面へ「運営者ならば通す」を足す | どちらの理由で通ったのかが読めなくなる |
| 運営者へ組織の中身の全閲覧を許す | 応募者の個人情報を扱う。復旧に必要な範囲を超える |
| 運営者の経路へ 403 を返す | 運営者の経路が存在することだけが分かる |
| 運営者の操作を履歴へ残さない | 誰が復旧したかを後から追えない |

## 影響

- 最初の運営者は、サーバーの運用者が `bin/rails` のタスクで作る。
  手順は README（日英）へ記載した
- 運営者は組織の削除、アカウントの停止、応募や求人の閲覧を行えない。
  必要になった場合は、その都度どこまで許すかを判断する
- 運営者の付与・剥奪そのものは履歴へ残らない。
  誰がいつ運営者になったかは、サーバーの操作記録に依存する
- 管理者が 0 人になった組織は、運営者が管理者を立て直せる。
  ADR 0013 の「影響」に残していた復旧手段の欠落は、これで解消した
