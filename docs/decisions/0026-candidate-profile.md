# ADR 0026: プロフィールをアカウントと分けて持ち、必須項目を 1 つに絞る

- 状態: 採用
- 決定日: 2026-08-02

この文書は日本語版を正本とする。

## 背景

P6 Candidate Profiles は、求職者が応募に使う情報を扱う。
基本プロフィール、職歴、学歴、スキル、希望条件、公開範囲、
履歴書、エクスポート、削除・匿名化を含む。

プロフィールはアカウントに 1 つだけ紐づく。
`users` へ列を足す方法もある。

プロフィールは応募者の個人情報そのものである。
どこから見えるかを最初から決めておかないと、
後から公開範囲を足すときに「すでに見えていたもの」を隠せない。

採用の場面では、集めた情報そのものが判断を歪めうる。
持っていれば見えるし、見えれば判断に混ざる。

## 決定

- プロフィール（`candidate_profiles`）はアカウントへ 1 対 1 で従属する。
  `users` へ列を足さない
- アカウントを削除したらプロフィールも消える
- `user_id` は作成後に変更できない
- 表示名だけを必須とし、自己紹介・所在地・希望職種は任意とする
- **生年月日・性別・顔写真の列を持たない**
- 経路は `/:locale/profile`（単数）とし、ID を受け取らない
- 他のアカウントのプロフィールを見る経路は、公開範囲を決めるタスクまで作らない
- プロフィールがまだない場合は、作成の画面へ送る

## 理由

アカウントと分けるのは、寿命と公開範囲が違うためである。
認証に使う情報（メールアドレス、パスワード）はログインのためだけに要る。
プロフィールは応募のときに企業へ渡る。
削除・匿名化（P6 の対象範囲）では、アカウントを残して
プロフィールだけを消す選択肢がありうる。
同じ表に入れると、その選択ができない。

`user_id` を変更できなくするのは、付け替えられると
他人のプロフィールを自分のものにできるためである。

必須を表示名だけにするのは、埋まっていない項目があっても
プロフィールを作れる状態にするためである。
必須が多いと、作成の途中で止まったまま何も登録されない。

生年月日・性別・顔写真を持たないのは、
採用の判断に使ってはならない情報だからである。
「持っているが使わない」は成り立たない。
企業側の画面に出れば見えるし、見えれば判断に混ざる。
年齢や性別が必要になる場面（法定の統計など）が生じたら、
そのときに用途を限定した別の仕組みとして設計する。

経路が ID を受け取らないのは、他人のプロフィールを指す方法を作らないためである。
`/:locale/profiles/:id` を用意して権限を確かめる形にすると、
確かめ忘れがそのまま他人の個人情報への入口になる。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| `users` へ列を足す | 寿命と公開範囲が違う。アカウントを残してプロフィールだけ消せない |
| `user_id` を変更できるようにする | 他人のプロフィールを自分のものにできる |
| 必須項目を増やす | 作成の途中で止まったまま何も登録されない |
| 生年月日・性別・顔写真を持つ | 採用の判断に使ってはならない情報が、見えることで判断に混ざる |
| `/:locale/profiles/:id` の形にする | 権限の確かめ忘れが、他人の個人情報への入口になる |
| 未作成でも空の詳細を見せる | 次に何をすればよいかが伝わらない |

## 影響

- プロフィールは本人しか読み書きできない。
  企業側から見える経路は、公開範囲を決めるタスクで作る
- 職歴・学歴・スキル・希望条件は別のテーブルとして足す。
  1 つのプロフィールに複数の職歴が並ぶためである
- 履歴書・職務経歴書の添付は、ファイルの保存先を決めるタスクで扱う
- エクスポートと削除・匿名化は、対象となる表がそろってから設計する
- プロフィールの完成度は、項目がそろってから判断する
