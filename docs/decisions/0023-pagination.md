# ADR 0023: ページ分割を自前の値オブジェクトで行う

- 状態: 採用
- 決定日: 2026-08-02

この文書は日本語版を正本とする。

## 背景

P5 の対象範囲は「ページネーション」を含む。

公開求人の一覧は、条件に一致するすべての求人を 1 画面へ出していた。
求人が増えると応答が重くなり、閲覧者は目的の求人へ届きにくくなる。

`docs/development/workflow.md` は「新規依存を勝手に追加しない」としている。
ページ分割の gem（Kaminari、Pagy）は広く使われているが、
必要としているのは「何件目から何件」と「前後のページがあるか」の 2 つだけである。

ADR 0020 で、`page` を持つ URL の canonical をどう出すかを
このタスクで決めると残した。

## 決定

- ページ分割は値オブジェクト `Pagination` として自前で持つ。gem を足さない
- 1 ページの件数は 20 件とする
- ページ番号は `page` の query string で表す
- 範囲外のページ番号（0、負の数、数字でない値、総ページ数超）は
  1 ページ目へ丸める。エラーにしない
- 0 件でも総ページ数は 1 とする
- 条件を持たない一覧の canonical は、そのページ自身の URL とする
- 条件を持つ一覧の canonical は、条件もページも持たない URL とする
- 前後のページへの導線だけを出し、ページ番号の一覧は出さない
- `rel="prev"` / `rel="next"` を導線へ付ける

## 理由

gem を足さないのは、必要な機能が小さいためである。
`limit` と `offset`、総件数、前後の有無だけで足りる。
依存を 1 つ増やすと、その更新と脆弱性の追跡が続く。
表示の柔軟さが要るようになった時点で、あらためて判断する。

1 ページ 20 件にするのは、狭い画面でも一覧をたどれる長さだからである。
求人 1 件が題名・組織名・勤務地の 3 行を占めるため、20 件で 60 行程度になる。

範囲外を丸めるのは、404 を返す理由がないためである。
URL を手で書き換えた場合や、求人が減ってページが消えた場合に、
1 ページ目を見せる方が閲覧者の意図に近い。

0 件でも 1 ページとするのは、「0 ページ目」を表示する画面がないためである。

条件を持たない 2 ページ目以降の canonical をそのページ自身にするのは、
1 ページ目の複製として扱うと、そこにしかない求人が索引されないためである。
条件を持つ一覧はすでに `noindex, follow` であり、
canonical は条件を持たない一覧を指す（ADR 0021）。

ページ番号の一覧を出さないのは、件数が増えるほど番号が並び、
どれを押せばよいかの手がかりにならないためである。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| Kaminari / Pagy を入れる | 必要な機能が小さい。依存の更新と脆弱性の追跡が続く |
| 範囲外のページ番号で 404 を返す | URL の書き換えやページの消滅で、閲覧者が行き止まりになる |
| 2 ページ目以降の canonical を 1 ページ目にする | そこにしかない求人が索引されない |
| ページ番号の一覧を出す | 件数が増えるほど番号が並び、手がかりにならない |
| 無限スクロールにする | JavaScript に依存し、URL でページを指せなくなる |
| 1 ページの件数を利用者が選べるようにする | URL の種類が増え、canonical の判断が複雑になる |

## 影響

- `offset` を使うため、後ろのページほどデータベースの走査が増える。
  求人が大量になった場合の応答は P11 で観測する
- 総件数を毎回数える。`count` の費用は件数に比例する
- 総件数を画面へ出していない。「何件中何件目」は表示しない
- 組織側の管理画面の一覧はページ分割していない。
  1 組織が持つ求人の数が問題になった時点で判断する
