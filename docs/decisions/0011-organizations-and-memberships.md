# ADR 0011: 組織と所属を分けて持ち、所属が役割を持つ

- 状態: 採用
- 決定日: 2026-08-01

この文書は日本語版を正本とする。

## 背景

P3 Organizations and Authorization は、組織、メンバー、招待、ロール、権限、
組織間のデータ分離を扱う。

これらはすべて「誰がどの組織に、どんな立場で属しているか」の上に載る。
その表し方は後から変える費用がとくに高い。
所属の形が変わると、権限の判定、データの絞り込み、招待の経路のすべてが影響を受ける。

## 決定

- 組織（`organizations`）と所属（`memberships`）を別のテーブルとして持つ
- アカウントへ直接 `organization_id` を持たせない
- 1 人のアカウントは複数の組織へ所属できる。同じ組織へは 1 度だけ
- 役割は所属が持つ。組織でもアカウントでもない
- 役割の初期集合は `owner` と `member` の 2 つとする
- 組織を作成したアカウントは、その組織の `owner` になる
- 組織と最初の所属は同じトランザクションで作る。責務はモデル
  （`Organization.create_with_owner!`）へ置く
- 組織名は一意にしない
- 組織の一覧には、閲覧者が所属する組織だけを出す

## 理由

組織と所属を分けるのは、1 人が複数の組織に関わるためである。
採用の現場では、代理店や兼務によって複数の組織の求人に関わる担当者がいる。
アカウントへ `organization_id` を持たせると、この状況を後から追加できない。
追加するには、既存のすべての参照を書き換えることになる。

役割を所属へ持たせるのは、同じ人が組織ごとに違う立場になるためである。
アカウントへ役割を持たせると、ある組織では管理者、別の組織では一般、
という当たり前の状態を表せない。

役割を 2 つから始めるのは、制限したい操作がまだ決まっていないためである。
使い道のない役割を先に並べても、どこで効くのかを誰も判断できない。
役割の細分化は、制限する操作が決まってから足す。

作成者を `owner` にするのは、誰も入れない組織を作らないためである。
作成した直後に管理者がいない状態を許すと、招待もできない組織が残る。

組織名を一意にしないのは、同名の組織が実在するためである。
一意にすると、後から登録する組織が名前を変えることになる。
組織を URL で指す方法（識別子）は、公開ページを作るタスクで別途決める。

一覧を所属する組織だけに絞るのは、
すべての組織を出すと一覧そのものが「どんな組織が登録されているか」を
調べる手段になるためである。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| アカウントへ `organization_id` を持たせる | 1 人が複数の組織に関わる状況を後から追加できない |
| 役割をアカウントへ持たせる | 組織ごとに違う立場を表せない |
| 役割を組織へ持たせる | 誰の役割かを表せない |
| 役割を最初から細かく分ける | 制限したい操作が決まっておらず、どこで効くのか判断できない |
| 組織名を一意にする | 同名の組織が実在する。後から登録する側が名前を変えることになる |
| 作成直後は管理者なしとする | 招待もできない組織が残る |
| すべての組織を一覧に出す | 登録済みの組織を調べる手段になる |

## 影響

- 権限の判定は、これ以降すべて「その組織における所属の役割」を見る形になる
- 組織を URL で指す識別子（slug など）はまだない。
  公開ページを作るタスクで決める
- 組織の編集と削除の画面はまだない
- 招待は、まだ存在しないアカウントも対象になりうる。
  その扱いは招待を作るタスク（P3-T2）で決める
- 組織を削除すると所属も消える。組織に紐づく他のデータの扱いは、
  そのデータを作るタスクで決める
