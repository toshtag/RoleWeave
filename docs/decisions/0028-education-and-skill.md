# ADR 0028: 期間の規則を切り出し、スキルは名前で重複を拒否する

- 状態: 採用
- 決定日: 2026-08-02

この文書は日本語版を正本とする。

## 背景

P6 の対象範囲は「学歴」と「スキル」を含む。
ADR 0026 に、これらは別のテーブルとして足すと記録した。

学歴は職歴と同じ形をしている。
学校名と在籍期間を持ち、在学中は終了日を持たない。
ADR 0027 で決めた期間の規則（終了日は任意、開始日より前を拒否、
未来の開始日を拒否、開始日の降順）が、そのまま当てはまる。

スキルは期間を持たない。名前と経験年数だけを持つ。
同じスキルが 2 つ並ぶと、読み手はどちらが正しいか判断できない。

## 決定

- 期間の規則を `HasPeriod`（`app/models/concerns/has_period.rb`）へ切り出し、
  職歴と学歴の両方から使う
- 学歴（`educations`）はプロフィールへ従属する。学校名と入学日を必須とする
- 専攻・学位は任意とする
- スキル（`skills`）はプロフィールへ従属する。名前を必須とする
- 経験年数は任意とし、0 以上 80 以下の整数とする
- **同じプロフィールに同じ名前のスキルを 2 つ登録できない。**
  データベースの一意索引でも拒否する
- スキルの一覧は名前の昇順とする
- プロフィールを起点に対象を引く処理を
  `CandidateProfileScope` へ切り出し、職歴・学歴・スキルの経路から使う
- 経路はプロフィールの下（`/:locale/profile/educations`、`/:locale/profile/skills`）へ置く

## 理由

期間の規則を切り出すのは、同じ検証を 2 つのモデルへ書くと
片方だけ直した状態が生まれるためである。
「未来の開始日を拒否する」を職歴だけで直し、学歴で直し忘れると、
同じ画面の中で規則が食い違う。

規則を含むモデルの一覧をテストで固定した。
新しいモデルが期間の列を持ちながら `HasPeriod` を取り込まない場合、
そのテストが落ちる。取り込み忘れは、規則が効かないまま静かに残るためである。

スキルの重複を拒否するのは、同じ名前が 2 つ並ぶと
読み手がどちらを信じるか判断できないためである。
経験年数が違う 2 行が並ぶと、なおさら判断できない。
検証だけでは同時の登録をすり抜けるため、一意索引も置く。

経験年数に上限を置くのは、人が働ける長さを超える値が入力の誤りだからである。
上限がないと、桁を間違えた値（50 を 500 と打つ）がそのまま出る。

スキルを名前の昇順にするのは、経験年数を主にすると
未入力のスキルをどこへ置くかを決めることになるためである。
先頭に置けば実態より強く見え、末尾に置けば埋もれる。

`CandidateProfileScope` を切り出すのは、同じ処理を 3 つの Controller へ書くと
片方だけ直した状態が生まれるためである。
組織側の `OrganizationScope` と同じ形にそろえた。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| 期間の規則を職歴と学歴の両方へ書く | 片方だけ直した状態が生まれ、規則が食い違う |
| 学歴と職歴を 1 つのテーブルにまとめる | 学校名と会社名、専攻と役職が同じ列に入り、意味が読めなくなる |
| スキルの重複を検証だけで拒否する | 同時の登録をすり抜ける |
| スキルの重複を許す | 経験年数の違う 2 行が並び、どちらが正しいか判断できない |
| スキルを経験年数の降順で並べる | 未入力のスキルの置き場所を決めることになる |
| スキルを候補から選ばせる | 候補の一覧を誰が管理するかを決めることになる。自由入力で始める |
| 経験年数に上限を置かない | 桁を間違えた値がそのまま出る |
| 学位・専攻を選択肢にする | 国と学校で体系が違い、選択肢に載らない経歴が書けなくなる |

## 影響

- スキル名は自由入力のため、表記の揺れ（`Ruby` と `ruby on rails`）が残る。
  重複の判定は完全一致であり、揺れた名前は別のスキルとして並ぶ
- 資格・語学は扱っていない。スキルとして書ける。
  独立した項目が要るかは、企業側が候補者を探す仕組みを作るときに判断する
- `HasPeriod` を含むモデルを足す場合は、`has_period_test.rb` の一覧へも足す
- 学歴とスキルは本人しか読み書きできない。企業側から見える経路は、
  公開範囲を決めるタスクで作る
