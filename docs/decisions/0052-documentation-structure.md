# ADR 0052: 文書はロール別に分け、スクリーンショットを持たない

- 状態: 採用
- 決定日: 2026-08-02

この文書は日本語版を正本とする。

## 背景

P12 の完了条件は「ロール別の操作手順が文書化されている」
「セットアップ文書だけで第三者が起動できる」
「コントリビューションガイドとセキュリティポリシーが存在する」を含む。

対象範囲には「スクリーンショット」「操作動画」も含まれる。

README には起動の手順があるが、**起動した後に何をすればよいか**がなかった。
求職者として使うのか、企業として使うのかで、通る画面がまったく違う。

ADR は 52 件ある。初めて読む人が全部を読むことは期待できない。

## 決定

- 操作手順を**ロール別に 3 つ**に分ける（求職者 / 企業の担当者 / 運営者）
- 手順は**やりたいことから引ける表**の形にする。画面の名前を目次にしない
- 手順にはデモデータ（ADR 0051）のアカウントで追える前提を書く
- アーキテクチャの概要を 1 つ書き、そこから ADR を引けるようにする
- **意図的に持たないもの**を概要へ書く
- コントリビューションガイドへ、負の検証の要求を書く
- **スクリーンショットと操作動画を作らない**

## 理由

ロール別に分けるのは、通る画面が重ならないためである。
1 つの文書へまとめると、読み手は自分に関係のない節を読み飛ばすことになる。
読み飛ばした先に、自分に必要な記述が混ざる。

やりたいことから引く形にするのは、画面の名前を知らない人が読むためである。
「プロフィールの公開範囲の編集画面」ではなく「公開範囲を決める」から引く。

概要から ADR を引けるようにするのは、52 件を順に読ませないためである。
判断の理由は ADR にあり、概要はその索引として働く。

意図的に持たないものを書くのは、**ないことが設計だと伝えるため**である。
候補者の検索がないのは、作っていないからではない。作らないと決めたからである。
書かなければ「未実装」と読まれ、同じ議論が繰り返される。

負の検証を参加の条件へ書くのは、このリポジトリで実際に 10 件以上の
見落としが見つかっているためである。
「テストがある」ことと「テストが守っている」ことは別である。

**スクリーンショットを作らないのは、古くなるためである。**
画面は変わる。文書の更新と同時に撮り直す運用は続かない。
古い画面の画像は、書かれていない誤りより悪い。読み手はそれを現在の姿と信じる。
代わりに、**デモデータで実際の画面を見てもらう**（ADR 0051）。
撮った画像より、動く画面のほうが正確である。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| 操作手順を 1 つにまとめる | 自分に関係のない節を読み飛ばし、必要な記述も飛ばす |
| 画面の名前を目次にする | 画面の名前を知らない人が引けない |
| ADR を順に読ませる | 52 件ある。初めての読み手には多すぎる |
| 持たないものを書かない | 「未実装」と読まれ、同じ議論が繰り返される |
| スクリーンショットを載せる | 画面は変わる。古い画像は誤りより悪い |
| 操作動画を作る | 同じ理由。加えて、更新の手間が画像より大きい |
| 英語版の手順も書く | 更新が二重になる。まず日本語版を正本として維持する |

## 影響

- 画面を変えたときは、対応するロール別の手順を見直す必要がある。
  文書に URL を書いているため、経路の変更は必ず反映が要る
- 文書の経路が実在することは、いまは手作業で確かめている。
  自動で確かめる仕組みは持っていない
- 英語の読み手には、`SECURITY.md` と `CONTRIBUTING.md` の要約だけがある
- スクリーンショットがないため、README から画面の様子は分からない。
  デモデータを入れて実際に見てもらう前提である
