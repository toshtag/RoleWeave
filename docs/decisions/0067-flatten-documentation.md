# ADR 0067: 文書の重複を落とし、docs の階層を平らにする

- 状態: 採用
- 決定日: 2026-08-03

この文書は日本語版を正本とする。

## 背景

ADR 0052 で、文書をロール別に分け、スクリーンショットを持たないことを決めた。
その後 P13・P14・P15 と依存の棚卸しが進み、文書は 26 件（ADR を除く）へ増えた。

増えた結果、次の状態になっていた。

**同じ規則が 4 つのファイルに書かれていた。**
`docs/project-principles.md`、`docs/architecture/principles.md`、
`docs/quality/cross-cutting-requirements.md`、`docs/development/coding-style.md`。
最後の 1 つは冒頭で「正本は次の 3 ファイルとし、ここに規則を二重定義しない」と
宣言したうえで、その 3 ファイルの要約を書いていた。

**`docs/project-overview.md` は README の「このプロジェクトについて」と同じだった。**

**`docs/roadmap/` の 17 ファイルは、更新される見込みがなかった。**
P0 から P15 までの計画はすべて完了しており、
README に「以降は計画に沿って機能を足し続けない」と書いてある。
それでも「中長期計画の正本」として参照され続けていた。

**`docs/roadmap/post-v1-options.md` は ADR 0059 とほぼ同じ内容だった。**
候補 13 件はすべて未評価であり、需要シグナルは 1 件も発生していない。

**1 ファイルしかないディレクトリがあった。**
`docs/security/` は 1 件、`architecture/`・`quality/`・`performance/` は 2 件ずつ。

**運用の手順が `docs/development/` にあった。**
`docs/guides/operator.md`（運営者向け）から、「開発」の下を指していた。

**中身が名前から読めないファイルがあった。**
`docs/quality/verification-status.md` の中身は「満たしていない点」の一覧である。

## 決定

- 原則の 4 文書を `docs/principles.md` へ統合する
- `docs/project-overview.md` を削除する。README に無かった 2 行だけ README へ移す
- `docs/roadmap/` を削除する。フェーズの目的・非目標・完了条件は
  Git 履歴と Pull Requests から追う
- `docs/roadmap/post-v1-options.md` を削除し、ADR に無かった内容を
  [ADR 0059](0059-post-v1-evaluation.md) の追記へ移す
- `docs/` の直下を、読み手（使う・運用する・開発する）で分ける

```text
docs/
  principles.md      開発の原則
  architecture.md    何がどう組み合わさっているか
  known-gaps.md      満たしていない品質要件
  threat-model.md    何から守り、何を受け入れているか
  decisions/         ADR
  guides/            使う人向け
  operations/        運用する人向け
  development/       開発する人向け
```

- ADR の path は変えない。コードのコメントから 40 か所以上が指している
- 文書の移動に伴う path の書き換えは、ADR の本文へも直接適用する。
  判断そのものを変えていないためである

## 理由

同じ規則を 4 か所へ書かないのは、**どれが正本かを読み手が判断できない**ためである。
実際に `coding-style.md` は「二重定義しない」と宣言しながら二重定義していた。
書いた側は要約のつもりでも、読む側にはもう 1 つの正本に見える。

更新されない文書を残さないのは、**古い記述が現在の姿として読まれる**ためである。
これは ADR 0052 でスクリーンショットを作らないと決めたのと同じ理由である。
画面の画像が古くなるのと同様に、完了した計画の「予定」も古くなる。

ロードマップを Git 履歴へ委ねるのは、**それが実際に読まれる形だから**である。
どのフェーズで何を作ったかは、Pull Request の本文と検証結果とともに残っている。
YAML の `definition_of_done` を読むより、その方が情報が多い。

1 ファイルのディレクトリを畳むのは、**階層が中身を説明していない**ためである。
`docs/security/threat-model.md` の `security/` は、`threat-model` 以上のことを
何も伝えていない。

運用の文書を `operations/` へ移すのは、**運営者が「開発」の下を読まされない**ためである。
バックアップと逆プロキシは、このサーバーを動かす人が読む文書である。

名前を `known-gaps.md` へ変えるのは、`verification-status` が
「検証の状況」としか読めないためである。中身は未達の一覧であり、
**読ませたいのはそちらである。**

ADR の path を変えないのは、コードのコメントが指しているためである。
文書を読みやすくするために、コードを 40 か所書き換える取引は割に合わない。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| 4 つの原則文書をそのまま残し、相互参照を足す | 参照が増えるだけで、どれが正本かは変わらない |
| ロードマップを `archive/` へ移す | 追跡ファイルとして残る限り、古い記述は読まれる |
| ロードマップの `status` だけを更新し続ける | 誰も読まない YAML を更新し続けることになる |
| `docs/decisions/` を `docs/adr/` へ改名する | コードのコメント 40 か所以上を書き換えることになる |
| 実測と見積もりを 1 つの性能文書へまとめる | ADR 0050 が、混ぜると同じ確からしさに見えると決めている |
| README の文書一覧を 1 つの箇条書きのまま残す | 22 行の並びに意味がなく、自分に必要な文書を選べない |

## 影響

- 完全検証（`scripts/verify-p0`）の必須文書は 8 件から 3 件になる。
  ロードマップ YAML の構造検査（ID の一意性、index との突き合わせ、
  循環依存、P0 の検証コマンド）は、対象が無くなったため落とす
- 「P14 の対象範囲に挙げたが完了条件に含めていない」のような、
  フェーズの完了条件を根拠にした記述は、根拠を直接示す形へ書き換える必要がある
- ADR 0052 の「操作手順をロール別に 3 つへ分ける」は変えていない。
  `docs/guides/` はそのまま残る
- 文書の path が実在することは、いまも手作業で確かめている。
  自動で確かめる仕組みは持っていない（ADR 0052 の影響と同じ）
