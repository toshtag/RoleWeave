# ADR 0051: デモデータは実在しない領域を使い、development でだけ投入する

- 状態: 採用
- 決定日: 2026-08-02

この文書は日本語版を正本とする。

## 背景

P12 の完了条件は「架空データのみでデモシードが投入できる」を含む。

起動しても何も入っていない状態では、評価する人は
アカウントを作り、組織を作り、求人を作り、別のアカウントで応募して……と手で並べることになる。
そこまでして試す人は少ない。

一方、デモのために入れたデータが本物と混ざると、後から見分けられない。

## 決定

- rake タスク（`roleweave:demo:seed` / `clean`）で投入・削除する
- メールアドレスは **`@example.invalid`** とする（RFC 2606 の予約領域）
- 氏名・組織名・求人は、明らかに架空と分かるものにする（「デモ 太郎」「デモ株式会社」）
- 求職者 2 名・企業の管理者・企業の一般の所属者・運営者を作る
- 公開中に加えて、**下書きと審査中**の求人も作る
- 応募・選考の段階・評価・面接の予定・やり取り・通知まで入れる
- パスワードは共通とし、実行時に出力する
- **`Rails.env.development?` でなければ例外を投げる**
- すでに投入済みなら、二重に作らない

## 理由

`.invalid` を使うのは、実在しない領域だからである。
実在しそうなメールアドレスを使うと、
誤って通知が送られたときに、実在の相手へ届きうる。
`.invalid` 宛の送信は必ず失敗する。それが正しい振る舞いである。

架空と分かる名前にするのは、データベースを直接見た人が
「これは本物か」を考えずに済むようにするためである。

下書きと審査中の求人も作るのは、状態の違いが画面で見えるようにするためである。
公開中だけでは、審査の仕組み（ADR 0017）が何も見えない。

選考の段階を進め、やり取りまで入れるのは、
**画面が空にならない状態**を作るためである。
「応募はあるが選考はしていない」状態では、P8 と P9 の画面が空のままになる。

development に限るのは、架空データが本番のデータベースへ入ると
本物と混ざるためである。
`.invalid` で見分けられるとはいえ、入れないほうが確実である。

二重に作らないのは、繰り返し実行しても壊れないようにするためである。
評価する人は、うまく動かないときにもう一度実行する。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| `db/seeds.rb` へ書く | `db:setup` で自動的に入る。入れるかどうかを選べない |
| 実在しそうなメールアドレスを使う | 誤って実在の相手へ通知が届きうる |
| 公開中の求人だけを作る | 審査の仕組みが画面で見えない |
| 応募だけ作り、選考は進めない | P8 と P9 の画面が空のままになる |
| production でも実行できるようにする | 架空データが本物と混ざる |
| 実行のたびに作り直す | 評価中のデータが消える |

## 影響

- デモデータのアカウントはメールアドレスの確認済みとして作る。
  確認の流れそのものを試したい場合は、自分でアカウントを作る
- パスワードは共通であり、出力される。**公開環境で使ってはならない**
- 削除は `@example.invalid` のアカウントとデモの組織を対象とする。
  同じ領域のメールアドレスを手で作った場合、それも消える
- 大量データの投入は行わない。負荷試験は別のタスク（ADR 0050）が持つ
