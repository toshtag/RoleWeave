# ADR 0033: 削除は記録を残して匿名化し、唯一の管理者は削除させない

- 状態: 採用
- 決定日: 2026-08-02

この文書は日本語版を正本とする。

## 背景

P6 の完了条件は「削除または匿名化ができる」を含む。

ADR 0026 に「削除・匿名化では、アカウントを残して
プロフィールだけを消す選択肢がありうる」と記録した。

モデル側の後始末（`dependent`）はすでに整っている。
アカウントを消せば、プロフィール・職歴・学歴・スキル・希望条件・添付・
ログイン状態・所属は消える。履歴の参照は nullify される。

残っていたのは次の 2 つである。

1. `authentication_events.email_address` は、アカウントを消しても残る。
   `user_id` が空になっても、メールアドレスが残れば個人は特定できる
2. 組織の最後の管理者が消えると、その組織では以後誰も招待も変更もできなくなる。
   所属の変更にはこの制限があるが（ADR 0011）、アカウントの削除にはなかった

## 決定

- プロフィールだけの削除と、アカウントごとの削除を分ける
- どちらも確認を挟み、**何が消えるかを名前で示す**
- アカウントの削除には**パスワードの再入力**を求める
- **組織の唯一の管理者であるアカウントは削除できない。**
  対象の組織名を示す
- 削除と同じトランザクションで、認証の記録のメールアドレスを
  `deleted@anonymized.invalid` へ置き換える
- **認証の記録そのものは残す**
- 所属の履歴・求人の履歴も残し、参照だけを空にする（既存の動作）
- 判定と手順を `AccountDeletion` の 1 か所へ置く
- **判定は削除と同じトランザクションの中で、組織の行を押さえたまま行う。**
  画面へ出した時点の判定を、削除の時点でも使わない（ADR 0013）
- 確認の画面から、先にエクスポート（ADR 0032）へ導く

## 理由

プロフィールだけの削除を用意するのは、求職としての情報を引き上げても、
組織の一員としては使い続ける場合があるためである。
アカウントごと消すしかないと、退会か放置かの二択になる。

パスワードの再入力を求めるのは、ログイン状態だけで消せると
席を離れた端末からそのまま実行できるためである。
取り返しがつかない操作であり、いま操作しているのが本人であることを確かめる。

唯一の管理者を止めるのは、管理者が 0 人の組織が残ると
以後その組織で誰も招待も役割の変更もできなくなるためである。
所属の変更にはすでに同じ制限がある（ADR 0011）。
削除の側だけ抜けていると、同じ結果を別の入口から作れる。
「削除できません」だけでは何をすればよいか分からないため、組織名を示す。

判定を削除と同じトランザクションの中へ置くのは、
外で判定すると、判定してから削除するまでの間に owner が減りうるためである。
2 人の owner が同時に自分を削除すると、どちらも「もう 1 人いる」と判断する。
同じ理由で、判定の結果を保持しない。
画面を出した時点の答えを削除の時点でも使うと、その間の変化に気付けない。

認証の記録を残すのは、削除の前後の調査ができなくなるためである。
不正なログインの試行があった後にアカウントが消えた場合、
記録ごと消えると、何が起きたかを追えない。
一方、メールアドレスが残れば個人は特定できる。記録は残し、値だけを置き換える。

`.invalid` を使うのは、RFC 2606 で実在しないことが保証された
予約済みのトップレベルドメインであるためである。
誰かの本物のメールアドレスと衝突しない。

削除と匿名化を同じトランザクションへ入れるのは、
片方だけが残ると、消えたアカウントのメールアドレスが記録に残るためである。

確認の画面からエクスポートへ導くのは、
消す前に手元へ残せなければ、削除が「失う」だけの操作になるためである。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| 認証の記録ごと消す | 削除の前後の調査ができなくなる |
| メールアドレスを残したまま `user_id` だけ空にする | メールアドレスから個人が特定できる |
| 匿名化に実在しうるドメインを使う | 誰かの本物のメールアドレスと衝突しうる |
| パスワードの再入力を求めない | 席を離れた端末からそのまま実行できる |
| 唯一の管理者でも削除できるようにする | 管理者が 0 人の組織が残り、誰も操作できなくなる |
| 組織を道連れに削除する | 求人や、その組織のほかの所属者に影響が及ぶ |
| アカウントごとの削除だけを用意する | 退会か放置かの二択になる |
| 一定期間後に削除する（猶予期間） | 消えたつもりのデータが残る期間が生まれる。取り消しの経路も要る |

## 影響

- 添付の実体（blob）の削除は Active Storage の purge に従う。
  非同期のジョブとして実行されるため、キューが動いていない環境では
  ファイルが残る。運用は [`docs/development/file-storage.md`](../development/file-storage.md) を参照する
- 組織そのものの削除は用意していない。求人や所属が残るため、別に判断する
- 運営者が他人のアカウントを削除する経路は用意していない
- 削除の取り消しはできない。猶予期間も持たない
- 応募（P7）ができたら、応募の記録を削除時にどう扱うかを決める必要がある。
  企業側にとっては選考の記録であり、単純に消せるとは限らない
