# ADR 0027: 職歴の終了日を任意にし、並び順を開始日で固定する

- 状態: 採用
- 決定日: 2026-08-02

この文書は日本語版を正本とする。

## 背景

P6 の完了条件は「プロフィールと職歴を登録できる」を含む。

ADR 0026 で、職歴は別のテーブルとして足すと決めた。
1 つのプロフィールに複数の職歴が並ぶためである。

職歴には在籍中のものがある。
終了日を必須にすると、在籍中を表す方法がない。

職歴は並べて読まれる。並び順を決めないと、
保存した順や ID の順という、意味のない順で出る。

## 決定

- 職歴（`work_experiences`）はプロフィールへ従属する
- プロフィールを削除したら職歴も消える
- `candidate_profile_id` は作成後に変更できない
- 会社・団体名、役職、開始日を必須とし、業務内容と終了日を任意とする
- **終了日が空の職歴を在籍中として扱う**
- 終了日が開始日より前の職歴を拒否する。同じ日は受け入れる
- 未来の開始日を拒否する
- 一覧は開始日の降順で固定し、手で並べ替える仕組みを持たない
- 経路はプロフィールの下（`/:locale/profile/work_experiences`）へ置く
- 対象は本人のプロフィールを起点に引く

## 理由

終了日を任意にするのは、在籍中を表すためである。
必須にすると、在籍中の職歴を登録できないか、
「9999-12-31」のような実在しない日付を入れることになる。
後者は、値の見た目からは在籍中と読めない。

在籍中を画面で明示するのは、空欄が 2 つの意味を持つためである。
終了日の欄が空のままだと、在籍中なのか書き忘れなのかを読み手が判定できない。

未来の開始日を拒否するのは、まだ始まっていない職歴が
応募の時点で語れる経験ではないためである。
内定済みの入社予定は職歴ではない。

並び順を開始日で固定するのは、手で指定させると
職歴を足すたびに全体の並びを見直すことになるためである。
経歴は時間の順で読まれる。並べ替えたい理由が現れた時点で、その理由ごと設計する。

`candidate_profile_id` を変更できなくするのは、
付け替えられると自分の職歴を他人のプロフィールへ足せるためである。

経路をプロフィールの下へ置くのは、対象を本人のものへ限るためである。
`/:locale/work_experiences/:id` の形にすると、
経路ごとに「誰の職歴か」を確かめることになり、確かめ忘れが他人の経歴への入口になる。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| 終了日を必須にする | 在籍中を表せない。実在しない日付を入れることになる |
| 在籍中を別の真偽値の列で持つ | 終了日と食い違う状態を作れる（在籍中かつ終了日あり） |
| 終了日の空欄をそのまま出す | 在籍中か書き忘れかを読み手が判定できない |
| 並び順を手で指定できるようにする | 職歴を足すたびに全体の並びを見直すことになる |
| 未来の開始日を受け入れる | まだ始まっていない職歴は、応募の時点で語れる経験ではない |
| プロフィールの外へ経路を置く | 経路ごとの確かめ忘れが、他人の経歴への入口になる |
| 職歴をプロフィールの列（JSON）として持つ | 件数と項目の検証ができず、後から絞り込みも並べ替えもできない |

## 影響

- 在籍期間の長さは保存しない。必要になった時点で開始日と終了日から求める
- 会社名は自由入力とする。同じ会社が表記の揺れで別々に並びうる。
  名寄せは、企業側から候補者を探す仕組みが要るときに判断する
- 職歴は本人しか読み書きできない。企業側から見える経路は、
  公開範囲を決めるタスクで作る
- 学歴・スキル・希望条件も同じ形（プロフィールへ従属する別のテーブル）で足す
- エクスポートと削除・匿名化は、職歴を含めて設計する
