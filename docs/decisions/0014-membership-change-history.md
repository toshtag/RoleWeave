# ADR 0014: 所属と役割の変更をモデルのコールバックで記録する

- 状態: 採用
- 決定日: 2026-08-01

この文書は日本語版を正本とする。

## 背景

ADR 0013 で、役割の変更を管理者だけができるようにした。
ただし、変更そのものの記録は残っていない。

P3 の完了条件は「権限変更が履歴として残る」を含む。

ADR 0010 で認証の記録について
「記録は後から足すのが難しい。過去の出来事は復元できない」と書いた。
権限の変更にも同じことが当てはまる。
「いつからその人が管理者だったか」は、後から復元できない。

所属を作る経路は 1 つではない。
組織の作成、招待の受諾、役割の変更の 3 つがあり、今後も増える。

## 決定

- 所属の変更は `membership_events` テーブルへ 1 行ずつ記録する
- 記録する種類は `joined`（所属の追加）と `role_changed`（役割の変更）から始める
- 記録は `Membership` の `after_create` / `after_update` で行う
- 変更した主体（`changed_by`）を記録する。
  招待の受諾のように主体が本人の場合は本人を記録する
- 記録は、対象の組織とアカウントが削除されても残す（参照は `nullify`）
- 記録した内容（対象、種類、役割）は後から変更できない
- 履歴は組織の管理者だけが見られる
- 保存期間と削除処理は、この ADR では決めない

## 理由

記録をモデルのコールバックへ置くのは、所属を作る経路が複数あるためである。
Controller へ書くと、経路を足すたびに記録を書き足すことになり、
書き忘れがそのまま履歴の欠落になる。
モデルへ置けば、`Membership` を作る・変えるすべての経路が記録を伴う。

コールバックは一般に、副作用が見えにくくなるという欠点がある。
ここではその欠点より「記録の書き忘れが起きない」ことを重く見る。
記録は欠けたことに後から気付けない種類のデータである。

変更の主体を記録するのは、「誰が変えたか」が履歴の中心だからである。
主体は `Membership#changed_by` という保存しない属性で渡す。
アカウントを削除しても記録は残るため、参照は `nullify` する。

削除しても記録を残すのは、削除の前後の調査ができなくなるためである。
組織を削除した後で「その組織に誰がいたか」を問われることがある。

記録した内容を変更できなくするのは、
付け替えられると履歴が別の組織の話になるためである。

履歴を管理者に限るのは、誰がいつ役割を変えたかが
組織の運営に属する情報だからである。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| Controller で記録する | 所属を作る経路を足すたびに書き足すことになり、書き忘れが履歴の欠落になる |
| `authentication_events` へまとめる | 対象が違う。認証は人、これは組織の中の立場である |
| 対象の削除で記録も消す | 削除の前後の調査ができなくなる |
| 記録を後から編集できるようにする | 履歴が別の組織の話になる |
| 履歴を全メンバーへ開く | 組織の運営に属する情報である |
| 変更前の役割を持たない | 何がどう変わったかを復元できない |

## 影響

- `Membership` を作る・変えるたびに、書き込みが 1 回増える
- `MembershipEvent` は組織の削除で消さないため、
  組織スコープの構造検査（`organization_scoping_test`）からは
  理由を明記して外し、固有の契約を `membership_event_test` が持つ
- メンバーを組織から外す操作はまだない。
  外す操作を足すときは、対応する種類（`left` など）を記録へ加える
- 履歴の保存期間と削除処理を決めていない。現時点では無期限に残る。
  参照できる範囲とあわせて P10 Privacy, Security and Operations で決める
- 一覧に出すのは直近 50 件までとしている。全件を追う手段はまだない
