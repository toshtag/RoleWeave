# ADR 0060: Webhook の送信先は解決した IP で判定し、内部のアドレスへ繋がない

- 状態: 採用
- 決定日: 2026-08-02

この文書は日本語版を正本とする。

## 背景

ADR 0057 は送信先を http/https に限った。
scheme だけでは、**どこへ繋ぐか**は制限できない。

`http://127.0.0.1:5432/`、`http://169.254.169.254/latest/meta-data/`、
`http://10.0.0.5:8080/` は、いずれも http である。

アプリケーションのサーバーから出る接続は、外から出る接続とは届く範囲が違う。
自己ホストの構成では、データベースもジョブの実行基盤も同じネットワークに居る。
外からは届かない宛先へ、こちらのサーバーが代わりに繋ぐ形になる。

登録できるのは組織の管理者だけだが、**組織は誰でも作れる**。
脅威モデルの「求人を装う組織」と同じ前提であり、
外部の第三者がこの経路へ到達できる。

さらに、配信の結果は画面に出る。
例外のクラスとメッセージをそのまま残していたため、
接続を拒まれたのか、名前が引けないのか、応答が返ったのかの違いが読み取れた。
**その違いは、内部のどこに何が居るかを教える。**

## 決定

- 送信先の判定を `WebhookDestination` へ 1 か所で持たせる
- 拒否する範囲を値として閉じる。ループバック、私用、リンクローカル、
  ユニークローカル、旧サイトローカル、マルチキャスト、文書用、その他の予約済みを含む
- **廃止された範囲も拒否の側へ残す。**廃止は、配ってあるアドレスを消して回らない
- IPv4 を写した IPv6（`::ffff:127.0.0.1`）は、元の IPv4 として判定する
- **登録の時点では名前を解決しない。**書かれた値がそのまま IP の場合だけ判定する
- **配信の時点で名前を解決し、解決した IP へ接続する**
- 解決の結果が複数ある場合、そのすべてが許される場合だけ通す
- ホスト名は Host header と TLS の証明書の照合のために残す
- リダイレクトは追わない
- 環境変数 `WEBHOOK_ALLOWED_HOSTS` で明示したホスト名だけを例外とする。
  **既定は拒否とする**
- 失敗の内容は**種別だけ**を残す（`WebhookDelivery::FAILURE_REASONS`）

## 理由

判定を 1 か所へ置くのは、登録の画面と配信のジョブで別々に書くと
片方だけが緩んだ状態が生まれるためである（ADR 0013 と同じ考え方）。

拒否する範囲を値として閉じるのは、「内部かどうか」を後から数え上げると
数え漏れがそのまま抜け道になるためである。

**廃止された範囲を残す**のは、廃止が既に配ってあるアドレスを消さないためである。
IPv6 の `fec0::/10`（旧サイトローカル）は RFC 3879 で廃止されたが、
その範囲を内部で配っている環境は残りうる。
「もう使われていないはず」は、拒否の表から外す理由にならない。
表から外して困るのは、外した側ではなく、その範囲を使っている自己ホストの利用者である。

登録の時点で名前を解決しないのは、**解決しても意味がない**ためである。
登録の時点の答えと配信の時点の答えが同じである保証はない。
外部の IP を返してから内部の IP を返す（DNS rebinding）ことができる。
解決を登録の側へ置くと、防げないものを防いだつもりになり、
DNS が落ちている間に登録できなくなる副作用だけが残る。

配信の時点で解決し、**その結果の IP へ接続する**のは、
判定と接続の間に答えを変えられないようにするためである。
判定してから名前で繋ぎ直すと、2 回目の解決の答えが内部を指しうる。

解決の結果すべてを見るのは、1 つでも内部を指すなら
**どれへ繋ぐかによって結果が変わる宛先**だからである。

ホスト名を残すのは、TLS の証明書がホスト名に対して発行されるためである。
IP で繋ぎ、IP で照合すると、正当な https の送信先へ送れなくなる。

リダイレクトを追わないのは、判定を通った URL から内部の宛先へ飛べるためである。

明示の許可を残すのは、自己ホストでは内部の受け口が
正当な送り先である場合があるためである。
**既定を許可にしない。**設定を書かないまま動かした利用者が、
知らないうちにこの経路を開けている状態を作らない。

失敗の種別だけを残すのは、例外の内容が内部の状態を教えるためである。
運用のために何が起きたかは残す必要があるが、
「接続できない」と「相手が 401 を返した」の区別までは要らない。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| scheme だけを見る | どこへ繋ぐかを制限できない。いまの状態である |
| 登録の時点で名前を解決して終わりにする | 配信の時点で答えを変えられる（DNS rebinding） |
| 判定した後にホスト名で繋ぎ直す | 2 回目の解決の答えが内部を指しうる |
| 解決の結果の 1 つ目だけを見る | 残りが内部を指す宛先を通してしまう |
| 許可する宛先を一覧で持つ（既定で拒否） | 送り先は利用者が決める。一覧の維持を運営者へ負わせる |
| 内部の宛先を既定で許す | 設定を書かない利用者が、知らないうちに開けた状態になる |
| 例外の内容を画面へ出し続ける | 接続の可否が読み取れる。内部の探索に使える |
| 送信を別のネットワークへ隔離する | 運用の構成であり、アプリケーション側では決められない |

## 影響

- 内部の受け口へ送りたい場合、`WEBHOOK_ALLOWED_HOSTS` の設定が要る
- 名前の解決は配信のたびに行う。解決の結果は保存しない
- 失敗の理由が種別までになるため、細かい原因は送り先の側で確かめることになる
- `webhook_deliveries.error` の列は、メッセージではなく**種別**を持つ。
  列の名前は変えていない
- 登録の時点で通った宛先が、配信の時点で拒まれることがある。
  これは想定した挙動であり、履歴に種別として残る
- 拒否の表は、IANA の登録簿と RFC を根拠に人手で保つ。自動では取り込まない。
  範囲を足すときは、用途の分かる名前をコメントへ添える
