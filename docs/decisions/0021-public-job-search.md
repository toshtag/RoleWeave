# ADR 0021: 初期の求人検索を PostgreSQL の部分一致で行う

- 状態: 採用
- 決定日: 2026-08-01

この文書は日本語版を正本とする。

## 背景

P5 の完了条件は「キーワードと条件で絞り込める」と
「初期検索が PostgreSQL のみで動作する」を含む。
P5 の非目標は「OpenSearch の導入」である。

README の技術スタックは「初期段階では Redis、OpenSearch、Kubernetes を必須にしません」としている。

日本語の全文検索には、語の区切りを判定する仕組みが要る。
PostgreSQL の `to_tsvector` は、既定の設定では日本語を 1 つの塊として扱う。
拡張（pg_bigm、PGroonga）を入れれば解決するが、
どちらも `CREATE EXTENSION` を必要とし、
自己ホストの利用者が用意する PostgreSQL で使えるとは限らない。

## 決定

- キーワードは `ILIKE` による部分一致とする
- 対象の列は題名・仕事内容・職種・勤務地とする（`SEARCHABLE_COLUMNS`）
- 語を空白で分け、すべての語を含む求人だけを返す（AND）
- 入力は `sanitize_sql_like` を通し、`%` と `_` をそのままの文字として扱う
- 勤務地と職種は部分一致、雇用形態は決められた値との完全一致とする
- 決められていない雇用形態は、条件として無視する
- 絞り込みの条件はモデルの scope が持ち、Controller は受け取った値を渡すだけとする
- 条件は query string で表す
- 条件を持つ一覧の canonical は、条件を持たない一覧の URL とする
- 条件を持つ一覧は `noindex, follow` とする
- 全文検索の拡張と OpenSearch は導入しない

## 理由

部分一致を選ぶのは、拡張なしで日本語を扱える唯一の現実的な方法だからである。
`to_tsvector` の既定では「採用担当」が 1 語として扱われ、「採用」で一致しない。
部分一致であれば、語の区切りを判定しなくても一致する。

すべての語を含む条件（AND）にするのは、
いずれかを含む条件では語を足すほど結果が増え、絞り込みにならないためである。

`sanitize_sql_like` を通すのは、`%` を入力されたときに
すべての求人が一致してしまうためである。
利用者の入力を、検索の記号として解釈しない。

雇用形態で決められていない値を無視するのは、
一致する求人が 0 件になるより、条件がなかったものとして扱う方が
利用者の意図に近いためである。
値は選択肢からしか選べないため、それ以外は入力の誤りか改変である。

条件をモデルへ置くのは、絞り込みの経路が増えたときに
条件の組み立てが 2 か所へ分かれないためである。

条件を持つ一覧を索引させないのは、
同じ求人の集合へ無数の URL から到達できる状態を検索エンジンへ渡さないためである。
`follow` を残すのは、そこから各求人の詳細へたどってほしいからである。

## 制約

この方式には次の限界がある。分かったうえで採用する。

- **一致度による並び替えができない。** 結果は新しい順である
- **索引が効かない。** `ILIKE '%...%'` は前方一致でないため、
  通常の B-tree 索引を使えない。求人が増えると全件走査になる
- **表記のゆれを吸収しない。** 「エンジニア」と「ｴﾝｼﾞﾆｱ」は別の語として扱う
- **同義語を扱わない。** 「PM」と「プロジェクトマネージャー」は一致しない

求人の件数が増えて応答が問題になった時点で、
拡張の導入か検索基盤の分離を判断する。
その判断の材料は、P11 Performance and Observability で得る。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| `to_tsvector` による全文検索 | 既定の設定では日本語の語の区切りを判定できない |
| pg_bigm / PGroonga を入れる | `CREATE EXTENSION` を要し、自己ホストの環境で使えるとは限らない |
| OpenSearch を入れる | P5 の非目標。初期段階で必須の基盤を増やさない |
| いずれかの語を含む条件（OR） | 語を足すほど結果が増え、絞り込みにならない |
| 入力をそのまま `LIKE` へ渡す | `%` を入力されるとすべてが一致する |
| 決められていない雇用形態で 0 件にする | 条件がなかったものとして扱う方が利用者の意図に近い |
| 条件つきの一覧も索引させる | 同じ集合へ無数の URL から到達できる状態を検索エンジンへ渡す |

## 影響

- 求人が増えると検索の応答時間が伸びる。
  件数と応答時間の観測は P11 で行う
- 給与での絞り込みは、`salary` が自由記述のため行えない。
  構造化は別タスク（P5-T3）で扱う
- 並び替えの指定はない。結果は常に新しい順である
- ページネーションはまだない。条件に一致するすべての求人を返す（P5-T4）
