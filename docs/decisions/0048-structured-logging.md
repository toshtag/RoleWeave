# ADR 0048: 構造化ログを英語のキーで出し、個人情報を含めない

- 状態: 採用
- 決定日: 2026-08-02

この文書は日本語版を正本とする。

## 背景

P11 の完了条件は「構造化ログが英語キーで出力される」を含む。

既定のログは人が読む前提の文である。
「どの経路が遅いか」「どの要求が失敗したか」を数えるには、毎回その文を解析することになる。

商用の監視サービスへの依存は非目標である（P11 の `non_goals`）。
自己ホストの利用者が、標準出力を読むだけで扱える形にする必要がある。

ログは転送も保存もされる。公開範囲（ADR 0030）の設定は効かない。

## 決定

- 要求（HTTP）とジョブの完了を、**1 行の JSON**として出す
- キーはすべて**英語の snake_case**とする
- 出す項目を `StructuredLog` の 1 か所で決める
- **メールアドレス・氏名・本文を出さない**
- 利用者は id で表す
- **query string を出さない**
- 例外は種類とメッセージだけを出す。バックトレースは既定のログが持つ
- 値のない項目は出さない
- 既定のログは残す
- 新しい依存を足さない

## 理由

JSON にするのは、解析なしで読めるためである。
`jq` でも、外部の収集基盤でも、同じ行をそのまま扱える。

キーを英語にするのは、識別子であるためである
（`docs/development/language-policy.md`）。
利用者向けの文言ではなく、機械と運用者が読むものである。

個人情報を出さないのは、ログが公開範囲の外にあるためである。
アプリケーションの中では見せない設定にしていても、ログには残る。
利用者を id で表せば、追跡は成り立ち、漏えいの範囲は広がらない。

query string を出さないのは、絞り込みの条件に個人情報が入りうるためである。
求人の検索のキーワードは、その人が何を探しているかを表す。

依存を足さないのは、`ActiveSupport::Notifications` で足りるためである。
ログの形式のために依存を増やすと、自己ホストの構成が重くなる。

既定のログを残すのは、development で読めなくなるのを避けるためである。
production では、必要に応じて既定のログの水準を下げられる。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| 既定のログのままにする | 数えるたびに文を解析することになる |
| ログの整形に gem を入れる | 依存が増える。標準の仕組みで足りる |
| キーを日本語にする | 識別子であり、機械と運用者が読む。言語ポリシーに反する |
| メールアドレスを出す | 公開範囲の外へ個人情報を写すことになる |
| query string を出す | 絞り込みの条件に個人情報が入りうる |
| バックトレースを JSON へ入れる | 1 行が長くなり、機械で扱いにくくなる。既定のログが持つ |
| 外部の収集基盤へ送る | 商用サービスへの依存は非目標である |

## 影響

- ログの保存・回転は運用に委ねる。アプリケーションは標準出力へ出すだけである
- OpenTelemetry は導入していない。境界の設計は P11 の文書で扱う
- 監査ログ（ADR 0047）とは別である。監査ログは残す義務のある記録であり、
  構造化ログは運用のための出力である
- 出す項目を増やすときは `StructuredLog` を変える。
  そのとき、個人情報が入らないかを必ず確かめる
