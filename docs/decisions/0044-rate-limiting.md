# ADR 0044: 繰り返しに意味のある操作だけを IP 単位で制限する

- 状態: 採用
- 決定日: 2026-08-02

この文書は日本語版を正本とする。

## 背景

P10 の完了条件は「レート制限が機能する」を含む。
P2 から「ログイン・登録・再設定依頼の試行回数制限がない」を持ち越している。

Rails 8 は Controller の `rate_limit` を持つ。新しい依存は要らない。
数える場所は `Rails.cache` である。

test 環境の `cache_store` は `:null_store` だった。
この状態では数えられず、制限そのものを検証できない。

## 決定

- Rails の `rate_limit` を使う。新しい依存は足さない
- 対象は**繰り返すことに意味がある操作**だけとする。
  ログイン（総当たり）、登録（大量作成）、
  再設定の依頼（メールの大量送信）、メッセージの送信（相手への大量送信）、
  招待の作成（**任意の宛先への**メールの大量送信）
- 数える単位は IP アドレス（`rate_limit` の既定）とする
- **招待の作成では、認証・メールの確認・組織の解決・組織の管理者の判定を
  通った要求だけを数える**
- **メッセージの送信では、認証・メールの確認・応募の解決・参加者の判定を
  通った要求だけを数える**
- 上限と期間は `ApplicationController` の定数として 1 か所へ置く
- 超えた場合は 429 とし、**静的な画面**（`public/429.html` / `429.en.html`）を返す
- test 環境の `cache_store` を `:memory_store` へ変える
- テストの前に `Rails.cache.clear` を行う

## 理由

対象を絞るのは、すべての経路へ制限を掛けると
通常の利用が止まる場所が出るためである。
一覧の読み込みや画面の遷移は、繰り返しても害がない。

IP 単位にするのは、アカウント単位だと
「存在するアカウント」を外から探せてしまうためである。
特定のアカウントだけが早く止まれば、そのアカウントの存在が分かる。
アカウントを狙ったロックアウトも作れる。

招待を対象へ入れるのは、**届く先がこちらの利用者とは限らない**ためである。
再設定の依頼はそのアドレスの持ち主が登録している場合にしか送られないが、
招待は宛先を送る側が自由に決められる。
組織ごとに数えないのは、組織が確認済みのアカウントであれば作れるためである。
組織を単位にすると、作り直すだけで上限を迂回できる。

招待で認可の後に数えるのは、
**数える対象を「認証と必要な認可を通った要求」に合わせる**ためである。
Rails の `rate_limit` は宣言した位置へ `before_action` を登録する。
認証より前に書くと、認証・認可を通らない要求まで枠を減らす。
枠は IP 単位で共有されるため、それは同じ IP の管理者を止める手段になる。

メッセージで参加者の判定の後に数えるのも、同じ理由による。
枠は IP 単位で共有されるため、それは同じ IP の参加者を止める手段になる。

数える契機は Action の実行の直前である。
認可を通った後は、入力の検証に失敗した要求も数える。
ログインや登録のように認証を要しない入口では、認証前に数えるのが正しい。
そこでは「認証されていない要求」こそが抑えたい対象である。

上限を 1 か所へ置くのは、経路ごとに書くと片方だけ緩めた状態が生まれるためである。

429 に静的な画面を返すのは、ほかのエラー画面と同じ理由による（ADR 0003）。
制限が働いている状況は、負荷が高い状況でもありうる。

test 環境のキャッシュを変えるのは、`:null_store` では制限が働かないためである。
働かないまま「制限がある」と書くことはできない。
一方、キャッシュを持つとテストの間で数が持ち越される。
各テストの前に空にして、順番で結果が変わらないようにする。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| すべての経路へ制限を掛ける | 通常の利用が止まる場所が出る |
| アカウント単位で数える | 存在するアカウントを外から探せる。狙ったロックアウトも作れる |
| 招待を組織単位で数える | 組織は作れる。作り直すだけで上限を迂回できる |
| 招待の上限を認証より前で数える | 認証・認可を通らない要求で、同じ IP の管理者の枠を減らせる |
| メッセージの上限を認証より前で数える | 認証・認可を通らない要求で、同じ IP の参加者の枠を減らせる |
| 上限を経路ごとに書く | 片方だけ緩めた状態が生まれる |
| 429 を `head` だけで返す | 何が起きたのかが利用者に伝わらない |
| 429 を動的に描画する | 負荷が高い状況で、描画経路に依存することになる |
| test を `:null_store` のままにする | 制限が働かないまま「ある」と書くことになる |
| `rack-attack` を入れる | 新しい依存が増える。Rails の機能で足りる |

## 影響

- 同じ IP を共有する利用者（社内の網、携帯回線）は、互いの試行を数え合う。
  上限は通常の利用で届かない値に置いている
- **数える IP は、前段の逆プロキシの設定に依存する。**
  信じる前段を書かないと、`X-Forwarded-For` を変えるだけで数え直させられる。
  前提は ADR 0062 と `docs/development/reverse-proxy.md` が持つ
- production の数え場所は Solid Cache である。
  複数のプロセスで動かす場合、数はデータベースを通じて共有される
- 期間が過ぎると再び試せる。ロックアウトは行わない
- CAPTCHA は入れていない。自動化された試行を完全には止められない
- 制限の値は定数である。運用中に変えるには再起動が要る
