# ADR 0018: 求人の公開状態の変更をモデルのコールバックで記録する

- 状態: 採用
- 決定日: 2026-08-01

この文書は日本語版を正本とする。

## 背景

ADR 0017 で、求人の公開申請・審査・停止を作った。
その「影響」に、差し戻しと停止の理由を記録していないことを残した。

P4 の完了条件は「公開状態の変更が履歴として残る」を含む。

ADR 0014 で所属の変更について
「記録は後から足すのが難しい。過去の出来事は復元できない」と書いた。
公開状態にも同じことが当てはまる。
「いつからその求人が公開されていたか」は、後から復元できない。

求人は応募者が見るものであり、いつ公開され、いつ止まったかは
応募の受付期間そのものになる。

## 決定

- 公開状態の変更は `job_posting_events` テーブルへ 1 行ずつ記録する
- 記録は `JobPosting` の `after_create` / `after_update` で行う
- 作成時も記録する（`draft` として作られたこと）
- 変更した主体（`changed_by`）を記録する
- 対象の求人と組織が削除されても記録は残す（参照は `nullify`）
- 記録した時点の**題名**も併せて持つ
- 記録した内容（対象、状態、題名）は後から変更できない
- 履歴は、その組織の所属であれば役割を問わず見られる
- 保存期間と削除処理は、この ADR では決めない

## 理由

記録をモデルのコールバックへ置くのは、状態を変える経路が複数あるためである。
申請・承認・差し戻し・停止があり、今後も増える。
Controller へ書くと、経路を足すたびに記録を書き足すことになり、
書き忘れがそのまま履歴の欠落になる。
これは ADR 0014 と同じ判断による。

題名を併せて持つのは、求人が削除された後も
「何の記録か」が読める状態にするためである。
`job_posting_id` だけを持つと、削除後の履歴が空欄の並びになる。
これは記録の重複ではなく、その時点の事実の保存として扱う。

履歴を所属者全員へ見せるのは、差し戻された担当者が
いつ差し戻されたかを自分で確認できる必要があるためである。
ADR 0014 では所属の履歴を管理者だけに限ったが、対象が違う。
所属の変更は組織の運営に属し、求人の状態は日々の作業に属する。

保存期間を決めないのは、応募の受付期間としてどれだけ遡る必要があるかが
まだ分からないためである。P10 で参照範囲とあわせて決める。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| Controller で記録する | 状態を変える経路を足すたびに書き足すことになる |
| `membership_events` へまとめる | 対象が違う。所属は組織の中の立場、これは求人の状態である |
| 題名を持たない | 求人を削除した後の履歴が読めなくなる |
| 対象の削除で記録も消す | 応募の受付期間を後から確認できなくなる |
| 履歴を管理者だけに限る | 差し戻された担当者が理由を確認する手がかりを失う |
| 記録を後から編集できるようにする | 履歴が別の求人の話になる |

## 影響

- `JobPosting` を作る・状態を変えるたびに、書き込みが 1 回増える
- `JobPostingEvent` は組織の削除で消さないため、
  組織スコープの構造検査（`organization_scoping_test`）からは
  理由を明記して外し、固有の契約を `job_posting_event_test` が持つ
- 差し戻しと停止の理由は、まだ記録していない。
  「誰がいつ」だけが残る。理由の記録は別途判断する
- 一覧に出すのは直近 50 件までとしている。全件を追う手段はまだない
- 履歴の保存期間と削除処理を決めていない。現時点では無期限に残る
