# ADR 0013: 組織の操作を役割で制限し、権限のない操作を 404 で返す

- 状態: 採用
- 決定日: 2026-08-01

この文書は日本語版を正本とする。

## 背景

ADR 0011 で役割を `owner` と `member` の 2 つから始めると決め、
「役割の細分化は、制限する操作が決まってから足す」とした。

ADR 0012 で招待を作れる条件を「その組織に所属していること」だけにした。
入ったばかりのメンバーが、誰でも他の人を招待できる状態になっている。

P3 の完了条件は「ロールに応じて操作が制限される」を含む。

権限の確認は、書き忘れが直接の穴になる種類の処理である。
「確認を書いた場所だけが守られる」形にすると、
新しい経路を足すたびに書き忘れの機会が増える。

## 決定

- 対象の組織は、常に `current_user.organizations` から探す
  （`OrganizationScope#set_organization`）
- 権限がない操作と、存在しない組織への操作は同じ 404 を返す
- 招待の作成は `owner` だけができる
- メンバーの役割変更は `owner` だけができる
- メンバー一覧は、所属していれば役割を問わず閲覧できる
- 自分自身の役割は変更できない
- 組織の最後の `owner` を `member` へ変更できない
- 自分自身と最後の管理者の保護はモデル（`Membership`）の検証として持つ

## 理由

対象を `current_user.organizations` から探すのは、
権限の確認を「探し方」そのものへ埋め込むためである。
`Organization.find` で探してから権限を確かめる形にすると、
確認を書き忘れた経路が、そのまま他組織への入口になる。
探し方を共通の concern へ置けば、書き忘れは「組織が見つからない」形で現れる。

404 を返すのは、403 と分けると「その組織が存在すること」だけが
分かる状態になるためである。
組織の ID を順に試すことで、登録済みの組織の数と範囲が推測できる。

招待と役割変更を `owner` に限るのは、どちらも組織の構成を変える操作だからである。
メンバーを増やすことと、誰が管理できるかを決めることは、
組織の運営そのものに属する。

メンバー一覧を全員へ開くのは、誰と一緒に働いているかが分からないと、
自分の組織の状態を確認できないためである。
この一覧に出るのは、同じ組織の所属者だけである。

自分自身の役割を変更できないのは、誤って自分を降格させると
元へ戻せなくなるためである。管理者が自分だけの場合、
降格した瞬間にその組織を運営できる人がいなくなる。

最後の `owner` を守るのは、管理者が 0 人になると
以後その組織で誰も招待も変更もできなくなるためである。
この状態からの復旧は、運営者権限（P3-T6）を待つことになる。

保護をモデルへ置くのは、役割を変える経路が画面だけとは限らないためである。
Controller へ書くと、別の経路を足したときに同じ確認を書き直すことになる。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| `Organization.find` で探し、後から権限を確かめる | 確認を書き忘れた経路がそのまま他組織への入口になる |
| 権限がない操作へ 403 を返す | 「その組織が存在すること」だけが分かる |
| 招待を全員へ開く | 入ったばかりのメンバーが誰でも他の人を招待できる |
| メンバー一覧を `owner` に限る | 誰と一緒に働いているかを確認できない |
| 自分自身の降格を許す | 管理者が自分だけの場合、元へ戻せなくなる |
| 最後の管理者の降格を許す | 以後その組織で誰も招待も変更もできなくなる |
| 保護を Controller へ書く | 役割を変える経路を足すたびに、同じ確認を書き直すことになる |

## 影響

- 組織を対象とする画面を新しく足すときは、`OrganizationScope` を使う。
  使わない経路は、他組織のデータへ到達しうる
- 組織へ従属するレコードは `organization_id` を作成後に変更できない（P3-T4 で追加）。
  変えられると、自分の組織のレコードを他組織へ付け替えられる。
  この契約は「組織へ従属するモデルすべて」を対象に検査する（`organization_scoping_test`）
- メンバーを組織から外す操作はまだない。
  外す操作にも「最後の管理者」の保護が要る。実装するタスクで合わせて決める
- 権限変更が履歴として残らない。誰がいつ役割を変えたかを後から追えない（P3-T5）
- 組織をまたぐ運営者権限はない。
  管理者が 0 人になった組織を外部から復旧する手段がない（P3-T6）
- 役割は `owner` と `member` の 2 つのままである。
  求人の編集など、制限したい操作が増えた時点で細分化を判断する
