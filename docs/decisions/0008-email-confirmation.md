# ADR 0008: メールアドレスの確認を署名付き token で行う

- 状態: 採用
- 決定日: 2026-08-01

この文書は日本語版を正本とする。

## 背景

ADR 0005 で、メールアドレスの到達性は形式検証で判定せず、
確認メールの責務とすることを決めた。

P2-T4 でアカウント作成の経路を作った時点では、
形式が正しいだけの、実在しないメールアドレスでも登録できる。

P2 の完了条件は「メール確認前の利用範囲が制限される」を含む。
制限をかける前に、確認そのものの仕組みを決める必要がある。

確認リンクは、メールという保存も転送もされる媒体を経由する。
リンクを持つ者が確認を完了できるため、
リンクに何を含めるか、いつまで有効にするかは、後から緩めにくい。

## 決定

- 確認済みかどうかは `users.confirmed_at` の有無で表す。真偽値は持たない
- 確認リンクの token は `generates_token_for` で作り、データベースへ保存しない
- token の有効期限は 24 時間とする
- token へ `email_address` を含め、確認先を変えた時点で発行済みのリンクを無効にする
- token は URL のパスへ置く。query string へは置かない
- 確認は `GET` で受ける
- すでに確認済みのアカウントで再度たどっても、失敗として扱わない
- 失敗の理由（壊れている、期限切れ、確認先の変更後）を画面で区別しない
- 確認メールは、登録した画面のロケールの言語で送る
- 確認メールはテキストのみとし、平文のパスワードを含めない
- 重複するメールアドレスでの登録は、これまでどおり画面で拒否する。
  「登録済みかどうかを隠すために、同じ応答へ寄せる」方式は採らない

## 理由

`confirmed_at` を時刻にするのは、いつ確認したかが後から要るためである。
問い合わせや調査で「いつから使えていたか」を答えるとき、真偽値では答えられない。

token を保存しないのは、保存すると漏えいした時点で
そのまま使える文字列がデータベースに残るためである。
署名付きの値を都度作れば、保存するものがない。

有効期限を 24 時間にするのは、短すぎるとメールを見る前に切れ、
長すぎると転送されたメールがいつまでも使えるためである。
確認は登録直後に行う操作であり、1 日あれば足りる。

token へ `email_address` を含めるのは、確認したい宛先が変わった後に
古いリンクが通ると、実在を確かめていないアドレスが確認済みになるためである。

token をパスへ置くのは、query string が Referer やアクセスログへ
残りやすいためである。

`GET` で受けるのは、メールのリンクが `GET` にしかならないためである。
状態を変える操作を `GET` で受けるのは通常避けるが、
ここではメールクライアントやセキュリティ製品がリンクを先読みする可能性を
受け入れたうえで、リンクの有効期限と 1 度きりでない性質で影響を抑える。

再度たどっても失敗にしないのは、リンクを 2 回たどるのが普通の操作であり、
そこで「無効なリンク」と出すと、確認できていないように見えるためである。

失敗の理由を区別しないのは、区別すると token を試すときの手がかりになるためである。

メールの言語を登録画面のロケールにするのは、
表示言語の正本を URL とする ADR 0001 の契約をメールでも保つためである。
`Accept-Language` や宛先ドメインから推測すると、
利用者が選んでいた言語と食い違う。

重複登録を同じ応答へ寄せないのは、費用と効果が釣り合わないためである。
寄せるには「すでに登録があります」というメールを送ったうえで、
画面には成功したかのような案内を出すことになる。
利用者は、打ち間違いで別のアドレスを入れた場合にも同じ画面を見るため、
メールが届かない理由を自分で切り分けられない。
一方で、登録の有無はログイン画面の応答時間やパスワード再設定の経路からも
推測されうるため、登録画面だけを隠しても効果が限られる。
推測の試行そのものを抑えるのは、試行回数の制限の役割とする。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| token をデータベースへ保存する | 漏えいした時点でそのまま使える文字列が残る |
| 確認済みを真偽値で持つ | いつ確認したかを後から答えられない |
| token を query string へ置く | Referer やアクセスログへ残りやすい |
| 確認を `POST` で受ける | メールのリンクは `GET` にしかできない |
| 確認済みのリンクを無効として扱う | 2 回たどるのは普通の操作であり、確認できていないように見える |
| 失敗の理由を画面で区別する | token を試すときの手がかりになる |
| 宛先や `Accept-Language` から言語を推測する | 利用者が選んでいた言語と食い違う |
| 重複登録を同じ応答へ寄せる | 打ち間違いと重複を利用者が切り分けられない。隠せる範囲も限られる |

## 影響

- アカウント作成のたびにメールが 1 通送られる。
  送信は `deliver_later` で行うため、実際の配送は Active Job の設定に依存する
- 確認前は、ログインが必要な画面のうち確認を求めるものへ入れない（P2-T7 で決定）。
  ログインとログアウトは確認前でもできる。拒むと、確認メールが届かなかった利用者が
  再送を依頼する手段まで失う
- 確認メールの再送、メールアドレスの変更は、この ADR では扱わない。
  どちらも token の発行条件に関わるため、実装するタスクで合わせて決める
- 登録画面は、メールアドレスが登録済みかどうかを外部から調べられる状態のままである。
  試行回数の制限を入れるタスクで、この経路も対象に含める
