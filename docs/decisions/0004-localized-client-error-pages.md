# ADR 0004: 400 と 422 をローカライズし、406 を別の機構として扱う

- 状態: 採用
- 決定日: 2026-08-01

この文書は日本語版を正本とする。

## 背景

ADR 0003 は 404 と 500 を静的 HTML とし、表示ロケールを元の URL から決めることを決めた。
そのうえで `400`・`406`・`422` の扱いを保留し、
「利用者が実際に到達する経路が確認できた時点で、同じ方式を適用するかどうかを別途判断する」と記録した。

到達経路を実測した。`Rails.application` へ
`action_dispatch.show_exceptions = :all` を与えて呼び出し、返る status を確認している。

| 状態 | 経路 | 結果 |
| --- | --- | --- |
| 400 | `/ja?a[]=1&a[b]=2`（query string の解析失敗） | status 400 |
| 400 | `/ja?a=%C0`（不正なバイト列） | status 400 |
| 422 | `POST /ja` | status 404（非 GET の route がないため到達しない） |
| 406 | 旧ブラウザーの User-Agent で `GET /ja` | status 406、英語の生成時ページ |

3 つは同じ「Rails 生成時のまま」に見えるが、返り方が同じではない。

- 400 と 422 は例外処理経路を通る。
  `ActionDispatch::ShowExceptions` が `config.exceptions_app` を呼び、
  `LocalizedPublicExceptions` が元の URL からロケールを決めて静的ページを返す
- 406 は例外ではない。`allow_browser` が登録する `before_action` が、
  `public/406-unsupported-browser.html` を直接描画して処理を止める。
  `exceptions_app` を通らないため、ADR 0003 のロケール解決はそのままでは効かない

## 決定

- `400` と `422` を、ADR 0003 と同じ方式でローカライズする
  - 日本語は `public/400.html`・`public/422.html` を正本とする
  - 英語は `public/400.en.html`・`public/422.en.html` とする
  - 構造とインライン CSS は 404・500 と同じものを使い、6 ページで `style` の内容を一致させる
- 422 は、現時点で到達経路がなくてもここでローカライズする
- `406` はこの ADR では実装せず、別のタスクで扱う。
  `exceptions_app` を通らないため、必要な変更が `public/` の追加では済まない
- 400 と 422 の文言は、原因を特定せずに読める説明とする。
  例外の種類、パラメーター名、送信内容を画面へ出さない

## 理由

400 をローカライズするのは、現に到達するためである。
日本語の URL から英語だけのページが返る状態は、
表示言語の正本を URL とする ADR 0001 の契約と食い違う。

422 を、到達経路がない段階でローカライズするのは、次の 2 つを比べた結果である。

- 到達経路（非 GET の route）を追加するのは P2 以降になる。
  そのタスクでページの追加を忘れると、最初のフォームで英語のページが本番へ出る
- ページを 1 組足す作業は、`exceptions_app` を共有しているため 400 と同じ手順で済む。
  一方、`public/` に方式の異なるページを 1 枚だけ残すと、
  次にここへ触る担当者が同じ判断をもう一度することになる

先に用意しておく側の費用が小さく、忘れたときの損失が本番の表示であるため、ここでそろえる。

到達経路がない状態でも、機構は検証できる。
`ActionController::InvalidAuthenticityToken` を例外処理経路へ流し、
`/ja` と `/en` それぞれで対応する静的ページが返ることをテストで固定している。
検証できるのは「例外から静的ページまで」であり、
「利用者の操作から例外まで」は経路を追加するタスクで初めて検証できる。

406 を分けるのは、機構が違うためである。
`allow_browser` の描画は Controller の中で起こる。
ロケールを反映させるには、描画するファイルの決め方と、
コールバックの実行順序（ロケールを適用する `around_action` と `before_action` の前後）を
同時に扱う必要がある。静的ページの追加とは変更の性質が異なるため、同じタスクへ混ぜない。

文言で原因を特定しないのは、400 と 422 が複数の原因で起こるためである。
400 は URL の解析失敗と本文の解析失敗の両方から、
422 は CSRF token の検証失敗と、今後追加する検証の失敗から到達する。
特定の原因を前提にした案内は、別の原因で到達した閲覧者にとって誤った指示になる。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| 422 をフォーム実装時まで延期する | 忘れたときの損失が本番の表示になる。方式の違うページが 1 枚だけ残る |
| 400 も延期する | 現に到達しており、日本語 URL から英語のページが返っている |
| 406 を同じタスクで実装する | `exceptions_app` を通らず、コールバック順序まで変更範囲が広がる |
| 400 と 422 を 1 つのページへまとめる | status code が閲覧者へ伝わらず、問い合わせ時の手がかりが減る |
| 例外の種類や送信内容を画面へ出す | 内部構造と入力値をそのまま外へ出すことになる |

## 影響

- 静的エラー画面が 6 ページになる。スタイルを変更するときは 6 ページすべてを同じ内容へそろえる
- 対応言語を追加するときは、`public/<status>.<locale>.html` を 6 つ追加する
- 422 へ到達する経路を追加するタスクでは、利用者の操作から 422 のページまでを通しで検証する。
  この ADR の時点で検証できているのは、例外処理経路から先だけである
- `public/406-unsupported-browser.html` は Rails 生成時のまま残る。
  対応ブラウザーの下限を満たさない閲覧者には、URL の言語に関わらず英語のページが返る
