# ADR 0001: 利用者向け URL へロケールを明示する

- 状態: 採用
- 決定日: 2026-07-31

この文書は日本語版を正本とする。

## 背景

このプロジェクトは日本語と英語を初期段階から同等に扱う。
対応言語を `ja` と `en` に限定し、既定を `ja`、翻訳のフォールバックを無効とする設定は P0 で確定している。

一方、利用者向けの画面はまだ存在せず、公開されている経路は稼働確認用の `/up` だけである。
P1 Application Shell では共通レイアウト、日英トップページ、言語切替、エラー画面を作る。
これらはいずれも「どの URL がどの言語を表示するか」に依存するため、
画面を作り込む前に URL とリクエストロケールの関係を決めておく必要がある。

この判断は後続タスクだけでなく、公開後の URL 互換性にも影響するため ADR として残す。

## 決定

- 利用者向けの HTML ページは、原則として `/:locale/...` 配下へ置く
- 初期の対応ロケールは `ja` と `en` とする
- `/` は既定ロケールの `/ja` へ 302 で遷移させる
- `/` へ同一の内容を直接描画しない
- 対応外のロケールを別の言語へフォールバックせず、route として受理しない
- URL のロケールは、そのリクエストの間だけ `I18n.locale` へ適用する
- Cookie、セッション、Accept-Language による自動切替は採用しない
- `/up` などの運用用 endpoint にはロケールを付けない
- 将来の言語切替は、明示的な URL へのリンクとして実装する

## 理由

URL だけで表示言語が決まるため、共有、ブックマーク、キャッシュ、テスト結果が決定的になる。
同じ URL が閲覧者の状態によって別の言語を返す設計では、
不具合の再現条件に「そのブラウザーの履歴」が含まれてしまう。

`/` を日本語ページとして直接描画すると、同じ内容が `/` と `/ja` の 2 つの URL に存在する。
リダイレクトにすれば、日本語の内容が置かれる URL は常に 1 つになる。

対応外ロケールを別の言語へフォールバックしないのは、
「欠落した翻訳を別の言語で補わない」という既存方針と同じ理由による。
`/fr` を日本語で返すと、未対応であるという事実が「動いている」状態に紛れる。

ロケールをリクエストの間だけ適用するのは、
グローバルな代入が残ると、あるリクエストの言語が別のリクエストへ漏れるためである。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| Cookie だけで言語を管理する | 同じ URL が閲覧者ごとに別の言語を返し、共有とテストが非決定的になる |
| セッションだけで言語を管理する | 同上。加えて未ログインの閲覧者にも状態を持たせることになる |
| Accept-Language で毎回自動的に切り替える | 閲覧者が明示的に選んだ言語を上書きし得る。判定の当否を URL から確認できない |
| `/` を日本語ページとして直接描画する | 同じ内容が 2 つの URL に存在する |
| 対応外の言語を日本語へ黙ってフォールバックする | 未対応であることを検出できなくなる |

## 影響

- 利用者向けの画面を追加するときは、`/:locale` 配下へ置く
- 言語切替は、対応するロケールの URL へのリンクとして実装する
- 運用用 endpoint は従来どおりロケールを付けずに追加する
- 対応ロケールを増やす場合は、`config.i18n.available_locales` の変更が route の制約へ反映される

Accept-Language を利用した言語の提案や、閲覧者の選択の記憶は、この決定と排他ではない。
必要になった時点で、URL を正本とする前提の上に追加できる。

この ADR は URL の構造と言語決定の経路だけを定めるものであり、
検索エンジンの扱いについては何も保証しない。
`hreflang`、正規 URL、sitemap は、公開向け画面を扱うフェーズで別途決定する。
