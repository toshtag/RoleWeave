# ADR 0043: 配信の失敗を通知へ記録し、再送は運営者だけが行う

- 状態: 採用
- 決定日: 2026-08-02

この文書は日本語版を正本とする。

## 背景

P9 の完了条件は「配信失敗が記録され再送できる」を含む。

通知メールは `deliver_later` で積むだけだった（ADR 0042）。
積んだ後に失敗しても、どこにも残らない。
利用者からは「通知が来ない」としか見えず、運営者は原因を追えない。

自己ホストの利用者は SMTP の設定を自分で行う。
設定の誤りは失敗として現れる。それが見えないことは、
「動いていないことに気付けない」ことを意味する。

## 決定

- 配信の状態を**通知そのもの**へ持たせる
  （`email_status` / `email_attempts` / `email_error` / `email_delivered_at`）
- 状態は `skipped` / `pending` / `delivered` / `failed` の 4 つとする
- `skipped` は「設定により送らない」であり、失敗ではない
- 送信は専用のジョブ（`NotificationEmailJob`）で行う。
  `deliver_later` を直接使わない
- 成功と失敗をジョブが記録する
- **例外は握り潰さない。**記録した後、そのまま投げ直す
- 失敗の内容（例外の種類とメッセージ）をそのまま残す
- 失敗した通知の一覧と再送は**運営者だけ**が扱う
- 再送は同じ通知に対して行い、通知を作り直さない
- 失敗の内容は運営者以外に見せない

## 理由

配信の状態を通知へ持たせるのは、通知 1 件に対して配信が 1 回だからである。
別の表にすると、通知と配信を突き合わせて読むことになる。
経路（メール以外）が増えた時点で、分けるかを判断する。

専用のジョブにするのは、`deliver_later` が結果を残さないためである。
積んだ時点で成功と見なす形では、「送ったつもり」しか分からない。

例外を握り潰さないのは、握り潰すとジョブの再試行が働かなくなるためである。
記録は残しつつ、失敗そのものは呼び出し側（ジョブの基盤）へ渡す。

`skipped` を失敗と分けるのは、設定で送らないことが正常だからである。
同じ状態にすると、失敗の一覧が「送っていないもの」で埋まる。

再送を運営者に限るのは、利用者に再送させると
同じ失敗を何度も繰り返させることになるためである。
SMTP の設定の誤りは、利用者側では直せない。

失敗の内容を運営者にだけ見せるのは、例外のメッセージが
サーバーの構成（ホスト名、認証の失敗）を含みうるためである。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| 配信の記録を別の表に持つ | 通知 1 件に配信 1 回であり、突き合わせが増えるだけ |
| `deliver_later` のまま失敗を追わない | 「送ったつもり」しか分からない |
| 失敗を握り潰して記録だけ残す | ジョブの再試行が働かなくなる |
| `skipped` を失敗として扱う | 失敗の一覧が、送っていないもので埋まる |
| 利用者が再送できるようにする | 直せない原因に対して、同じ失敗を繰り返させる |
| 失敗の内容を利用者へ見せる | サーバーの構成が漏れうる |
| 失敗を運営者へメールで知らせる | メールが送れない状況で、メールで知らせることになる |

## 影響

- 失敗の一覧は運営の画面にある。定期的に見に行く運用が要る。
  自動の通知はない（メールが送れない状況で、メールでは知らせられない）
- ジョブの再試行の回数と間隔は既定のままである。P11 で見直す
- `email_attempts` は、このジョブが数えた回数である。
  ジョブの基盤側の再試行もここへ加算される
- 配信の記録の保存期間は未定（P10）
- メール以外の経路（アプリ内は即時、将来の Webhook など）は状態を持たない
