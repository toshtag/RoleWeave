# ADR 0005: アカウントの識別子をメールアドレスとし、代入時に正規化する

- 状態: 採用
- 決定日: 2026-08-01

この文書は日本語版を正本とする。

## 背景

P2 Accounts and Sessions は、ログイン、パスワード再設定、メール確認を含む。
いずれも「どのアカウントか」を一意に決める識別子を必要とする。

識別子の規則は、後から変える費用がとくに高い部類に入る。
規則が緩いまま運用すると、同じ人が表記の違う複数のアカウントを作る。
後から統合するには、両方に紐づいた応募、メッセージ、権限をどう扱うかを決める必要があり、
決めた後もデータの移行が残る。

メールアドレスは、大文字小文字と前後の空白が違っても、
利用者にとっては同じ 1 つの宛先である。
`User@Example.com` と `user@example.com` で別のアカウントが作れると、
どちらでログインしたかによって見えるものが変わる。

## 決定

- アカウントの識別子はメールアドレス（`users.email_address`）とする
- 列名は `email_address` とする。`email` は使わない
- 値は代入の時点で正規化する。前後の空白を除去し、小文字へそろえる
- 正規化は Active Record の `normalizes` で行い、保存と検索の両方へ適用する
- 一意性はデータベースの一意インデックスで担保する。
  モデルの `uniqueness` 検証は、利用者へ理由を伝えるためのものと位置づける
- 形式の判定は `URI::MailTo::EMAIL_REGEXP` に委ね、独自の正規表現を書かない
- 長さの上限は 254 文字とする
- 実際に届くかどうかは形式検証で判定しない。確認メールの責務とする
- ユーザー名（handle）、電話番号、外部 ID をログイン識別子にしない

## 理由

メールアドレスを識別子にするのは、パスワード再設定と本人確認が
同じ宛先を使うためである。別の識別子を主にすると、
「ログインに使う値」と「本人へ到達できる値」が分かれ、
再設定の経路がどちらに紐づくのかを毎回決めることになる。

列名を `email_address` にするのは、Rails 8 が生成する認証の実装が
同じ名前を使うためである。将来 Rails 側の仕組みへ寄せるときに、
列名の差だけで書き換えが必要になる状態を作らない。

代入時に正規化するのは、保存だけを正規化すると
`find_by` へ渡した値との比較が表記に依存するためである。
`normalizes` は検索条件へも同じ変換を適用するため、
「登録はできるが、そのままでは見つからない」状態が生まれない。

一意性をデータベースへ置くのは、検証だけでは競合を防げないためである。
同じメールアドレスの登録が同時に 2 つ届くと、
どちらの検証も「まだ存在しない」と判断してから、両方が保存へ進む。

形式の判定を標準の正規表現に委ねるのは、
自作の正規表現が実在する書式を拒否する方向へ外れやすいためである。
とくに、記号を多く含む local part や新しい TLD は、
手書きの正規表現で落ちやすい。到達性は確認メールが確かめる。

長さの上限を置くのは、上限がないと索引に載らない長さの値を受け付けるためである。
254 文字は RFC 5321 が定める経路の最大長にそろえた値である。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| 列名を `email` にする | Rails 8 の認証実装と名前が分かれ、後で寄せるときに書き換えが必要になる |
| 正規化せず、`citext` 型で大文字小文字を無視する | 前後の空白の違いは吸収できない。型が PostgreSQL 固有になる |
| 正規化を保存時（`before_save`）だけに行う | 検索条件が正規化されず、登録できるが見つからない状態が生まれる |
| 一意性をモデルの検証だけで担保する | 同時に届いた 2 つの登録の間で重複を防げない |
| ユーザー名（handle）を識別子にする | 本人へ到達できる値と分かれ、パスワード再設定の経路が別に必要になる |
| 独自の正規表現で形式を判定する | 実在する書式を拒否する方向へ外れやすい |
| MX レコードの確認や到達性の検査を登録時に行う | 登録が外部の応答時間と可用性に依存する。到達性は確認メールで確かめる |

## 影響

- メールアドレスを変更する経路を作るときは、変更後の値も同じ正規化と一意性の規則へ従う。
  変更前の宛先への通知が必要かどうかは、その経路を作るタスクで決める
- 生の SQL、`insert_all`、`update_column` は正規化を経由しない。
  これらで書き込む経路を作るときは、呼び出し側で正規化する
- 大文字小文字を区別するメールアドレスを使う相手（RFC 上は local part の区別が許される）は、
  同じアカウントとして扱う。実運用でこの区別を行う配送先は事実上なく、
  区別する側の不都合より、同じ人が複数のアカウントを持つ不都合を重く見る
- 形式検証を通っても、実在しない宛先は登録できる。
  利用範囲の制限は、確認メールを扱うタスクで決める
