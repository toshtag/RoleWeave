# ADR 0057: Webhook は識別子だけを送り、失敗を業務処理から切り離す

- 状態: 採用
- 決定日: 2026-08-02

この文書は日本語版を正本とする。

## 背景

P14 の完了条件は「Webhook を登録し配信できる」
「失敗した連携が業務処理を止めない」「連携の実行結果が履歴として残る」を含む。

非目標に「個別サービス向け実装」「商用 SDK への直接依存」がある。
どこへ送るかは利用者が決める。こちらは**送る仕組み**だけを持つ。

**送り先はこちらの管理下にない。**
公開範囲（ADR 0030）も保持期限（ADR 0046）も、送った先には効かない。

## 決定

- Webhook（`webhooks`）は組織へ従属させる。管理できるのは**管理者だけ**
- 送る出来事の種類を選ぶ。選んでいない種類は送らない
- **送る本文に個人情報を含めない。**識別子と種類と時刻だけを送る
- 送信先は **http/https に限る**
- 署名の秘密を自動で作り、本文の HMAC-SHA256 を header へ付ける
- 秘密は**登録時にしか画面へ出さない**
- 配信はジョブで行い、**`after_commit` の後に積む**
- 配信の結果（`webhook_deliveries`）を残す。状態・応答コード・失敗の内容・試行の回数
- 例外は握り潰さない。記録した後、そのまま投げ直す
- 応答を待つ上限を 5 秒とする

## 理由

本文に個人情報を含めないのは、送り先がこちらの管理下にないためである。
氏名や本文を送れば、その先での扱いは相手に委ねられる。
削除の要求を受けても、送った先からは消せない。
識別子だけを送れば、受け取った側は必要に応じて API で取りに来る形になる
（その API の権限はこちらが決められる）。

http/https に限るのは、`file:` などを許すと
アプリケーションのサーバーから内部の別の仕組みを叩かせられるためである。

署名を付けるのは、受け取る側が「本当にこのサーバーからか」を確かめられるようにするためである。

秘密を登録時にしか出さないのは、画面に出し続けると
その画面を見られるだけで署名を作れるようになるためである。

`after_commit` で積むのは、**配信の失敗で業務処理が巻き戻らない**ようにするためである
（通知（ADR 0037）と同じ理由）。
応募が届いたことと、それを外部へ知らせられたことは別である。

例外を握り潰さないのは、握り潰すとジョブの再試行が働かないためである（ADR 0043 と同じ）。

上限を 5 秒にするのは、相手が遅いだけでジョブが埋まらないようにするためである。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| 本文へ応募者の情報を載せる | 送った先からは消せない。削除の要求に応えられなくなる |
| 送信先の scheme を制限しない | 内部の別の仕組みを叩かせられる |
| 署名を付けない | 受け取る側が送り主を確かめられない |
| 秘密を画面に出し続ける | 画面を見られるだけで署名を作れる |
| 同期で送る | 相手が遅いと業務処理が待たされる。失敗で巻き戻る |
| 失敗を握り潰す | ジョブの再試行が働かない |
| 個別のサービス向けに実装する | P14 の非目標である |
| 配信の順序を保証する | ジョブの基盤に依存する。順序が要る用途は別に設計する |

## 影響

- 受け取る側は、識別子から中身を取りに来る必要がある。
  そのための API は**まだない**。必要になった時点で設計する
- 配信の失敗は、組織の画面（配信先の一覧）でしか分からない。
  自動の通知はない
- 再試行の回数と間隔はジョブの既定に従う
- 配信の順序は保証しない
- 配信の記録は配信先の削除で消える。保持期限の対象にはしない
