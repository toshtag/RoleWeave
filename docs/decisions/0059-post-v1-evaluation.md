# ADR 0059: 需要シグナルのない候補は評価しない

- 状態: 採用
- 決定日: 2026-08-02

この文書は日本語版を正本とする。

## 背景

P15 Post-V1 Options は、13 個の候補を列挙している。
OpenSearch、SSO、カレンダー連携、CRM 連携、Slack、ビデオ会議、
高度な分析、AI による補助、マネージドホスティング、商用サポートなどである。

フェーズの `objective` は「このフェーズは検討候補の一覧であり、実装の約束ではない」と述べている。
非目標に「要望の裏付けがないままの実装着手」
「複数候補の同時着手」「列挙された全候補を一括して評価すること」がある。

完了条件は 3 つあり、そのうち 1 つは
**「需要シグナルが発生していない候補について、ADR の作成を完了条件としない」**である。

v0.1.0 を出したばかりであり、**利用者はいない。外部からの要望も届いていない。**

## 決定

- **需要シグナルが発生していない候補は評価しない。ADR も書かない**
- 需要シグナルを 4 種類に定義する
  （具体的な要望 / 実測 / 運用の実績 / 法令・契約）
- **「あると便利そう」はシグナルとしない**
- シグナルが発生したら、採用・不採用・**保留**のいずれかを ADR へ記録する
- 保留の場合は「何が起きたら再評価するか」を書く
- 採用した候補は、実装範囲・依存関係・非目標を持つ独立したタスクとして定義する
- 複数の候補を同時に着手しない
- 候補の一覧と現在の状態を `docs/roadmap/post-v1-options.md` へ残す

## 理由

シグナルのない候補を評価しないのは、**想像した要件に基づく設計になる**ためである。
「Slack 連携」と一言で言っても、何を、いつ、誰へ送るかで設計は変わる。
実際の要望が来る前に決めると、来たときに読み直すことになる。

「便利そう」を除くのは、それが選定の基準にならないためである。
候補は 13 個ある。すべてが「あると便利」である。
それを基準にすると、着手の順序が決まらない。

不採用も ADR に書くのは、同じ要望が再び来たときに経緯を読めるようにするためである。
「検討したが採らなかった」ことが残らないと、同じ議論が繰り返される。

保留に再評価の条件を書くのは、保留が「先送り」と区別できなくなるためである。
「利用者が 100 社を超えたら」のように、判断できる形で書く。

同時に着手しないのは、複数の候補が同時に未完成の状態を作らないためである。

**未評価のまま残る候補があることは、問題ではない。**
それは「まだ必要とされていない」ことを示している。
一覧を消化する対象として扱わない。

## 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| 13 個すべてに ADR を先に書く | 完了条件 3 に反する。想像した要件に基づく設計になる |
| 「便利そう」を基準に着手する | 13 個すべてが便利である。順序が決まらない |
| 不採用は記録しない | 同じ議論が繰り返される |
| 保留に条件を書かない | 保留と先送りが区別できない |
| 複数を同時に着手する | 同時に未完成の状態が増える |
| P15 を「実装しないフェーズ」として閉じる | 評価の手順が残らず、要望が来たときに毎回決め直す |

## 影響

- P15 は完了状態にできるが、**候補は 1 つも実装されていない**。
  これは設計どおりである
- 要望が来たときは、この ADR の手順に従って評価する
- `docs/roadmap/post-v1-options.md` は、要望が来るたびに更新する
- Slack・CRM 連携は、Webhook（ADR 0057）と CSV（ADR 0058）で部分的に代替できる。
  代替で足りるかも、シグナルが来たときに評価する
