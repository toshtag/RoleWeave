# v1 以降の検討候補

この文書は日本語版を正本とする。
判断の方針は [ADR 0059](../decisions/0059-post-v1-evaluation.md) を正本とする。

**これは実装の約束ではない。**
候補の一覧であり、着手するかどうかは需要シグナルが発生してから判断する。

## 現在の状態（2026-08-02）

**需要シグナルは 1 件も発生していない。**

v0.1.0 を出したばかりであり、利用者はいない。外部からの要望も届いていない。

したがって、**候補ごとの ADR は 1 件も書いていない**。
これは作業の漏れではなく、P15 の完了条件 3
（需要シグナルが発生していない候補について、ADR の作成を完了条件としない）に従った結果である。

シグナルのない候補を評価すると、次のことが起きる。

- 想像した要件に基づいて設計することになる
- 「検討済み」の記録だけが増え、実際の要望が来たときに読み直すことになる
- 一覧が長いほど、着手の判断が「消化」になる

## 需要シグナルとは

次のいずれかが 1 件でもあれば、その候補は評価の対象になる。

| 種類 | 例 |
| --- | --- |
| 具体的な要望 | Issue・Discussion・メールで「この機能がないと使えない」と述べられている |
| 実測 | 計測（[負荷試験](../performance/load-test-results.md)）が、その候補で解決する問題を示している |
| 運用の実績 | 自己ホストの運用で、手作業の回避策が繰り返し必要になっている |
| 法令・契約 | 対応しないと使えない要求が生じている |

**「あると便利そう」はシグナルではない。**
誰が、どの場面で、何ができずに困っているかが言えることを条件とする。

## 評価の手順

1. シグナルの内容を Issue へ書く（誰が・何に困っているか・どの候補で解決するか）
2. ADR を書く。**採用・不採用・保留のいずれか**を記録する
   - 採用しない場合も ADR を書く。同じ要望が再び来たときに、経緯を読める
   - 保留の場合は、**何が起きたら再評価するか**を書く
3. 採用した場合、独立したタスクを定義する
   - 実装範囲 / 依存関係（P13 や P14 が要るか）/ 非目標
4. 通常の進め方（Issue → ブランチ → PR）で実装する

**複数の候補を同時に着手しない**（P15 の非目標）。

## この文書の更新

シグナルが発生したら、その候補の行を「評価中」へ変え、ADR の番号を書く。
評価が終わったら「採用」「不採用」「保留」と、その ADR を書く。

**未評価のままの候補が残ることは、問題ではない。**
それは「まだ必要とされていない」ことを示している。
