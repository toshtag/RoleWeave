# 負荷試験の実測値

この文書は日本語版を正本とする。

測った値だけを書く。推測は「容量モデル」（[`capacity-model.md`](capacity-model.md)）へ書く。

## 測り方

```bash
docker compose run --rm app bin/rails "roleweave:load:seed[5000]"
docker compose run --rm app bin/rails "roleweave:load:measure[20]"
docker compose run --rm app bin/rails roleweave:load:clean
```

アプリケーションの中（`ActionDispatch::Integration::Session`）で測る。
外部の負荷ツールを足さない（ADR 0050）。

**この値に含まれないもの**: Puma のキュー待ち、リバースプロキシ、TLS、
ネットワーク、ブラウザーの描画。実際の利用者が体感する時間はこれより長い。

## 測った環境

| 項目 | 値 |
| --- | --- |
| 実行日 | 2026-08-02 |
| 実行場所 | Docker Compose の app コンテナ（開発機） |
| CPU | 8 コア（コンテナから見える値） |
| Ruby | 4.0.6 (aarch64-linux) |
| PostgreSQL | 15.18（コンテナのクライアント。サーバーは 18.4） |
| Rails 環境 | development |
| 同時実行 | なし（1 本ずつ順に 20 回） |

development で測っている。production では eager load とキャッシュの働きが違う。
**絶対値ではなく、データ量による増え方を見るための測定である。**

## 結果

### 求人 234 件

| 経路 | 状態 | p50 | p95 | 最大 |
| --- | --- | --- | --- | --- |
| 公開求人の一覧 | 200 | 12.3 ms | 24.4 ms | 370.1 ms |
| 公開求人の一覧（キーワード） | 200 | 16.0 ms | 21.7 ms | 21.9 ms |
| 公開求人の一覧（2 ページ目） | 200 | 11.1 ms | 14.7 ms | 15.1 ms |
| 公開求人の詳細 | 200 | 7.7 ms | 9.5 ms | 18.6 ms |
| トップページ | 200 | 6.1 ms | 7.9 ms | 22.3 ms |
| sitemap.xml | 200 | 19.7 ms | 22.5 ms | 58.0 ms |

### 求人 5,234 件（22 倍）

| 経路 | 状態 | p50 | p95 | 最大 | 234 件からの倍率（p50） |
| --- | --- | --- | --- | --- | --- |
| 公開求人の一覧 | 200 | 14.0 ms | 24.8 ms | 178.5 ms | 1.1 倍 |
| 公開求人の一覧（キーワード） | 200 | 67.8 ms | 74.3 ms | 86.3 ms | **4.2 倍** |
| 公開求人の一覧（2 ページ目） | 200 | 13.7 ms | 26.1 ms | 29.3 ms | 1.2 倍 |
| 公開求人の詳細 | 200 | 9.7 ms | 36.0 ms | 54.4 ms | 1.3 倍 |
| トップページ | 200 | 5.8 ms | 8.9 ms | 10.5 ms | 1.0 倍 |
| sitemap.xml | 200 | 306.1 ms | 474.1 ms | 557.9 ms | **15.5 倍** |

最初の 1 回は eager load とコネクションの確立を含むため、最大値へ現れる。

## 分かったこと

1. **sitemap.xml が件数にほぼ比例して遅くなる**（22 倍のデータで 15.5 倍）。
   公開中の求人をすべて 1 つの XML へ並べる作りであり、当然の結果である。
   ADR 0024 に「分割の閾値（5 万 URL / 50MB）に達した場合は索引 sitemap への分割が要る」
   と書いていたが、**その手前で応答時間が問題になる**
2. **キーワード検索が件数とともに遅くなる**（4.2 倍）。
   P5 から持ち越していた「`ILIKE '%...%'` は索引が効かない」が、数字として現れた
3. 一覧・詳細・トップページは、件数の影響をほとんど受けない。
   ページ分割（ADR 0023）と `includes`（ADR 0049 で固定）が効いている

## いつ直すか

| 対象 | 判断の基準 | 対応 |
| --- | --- | --- |
| sitemap.xml | 公開求人が 1 万件を超える、または p95 が 1 秒を超えた時点 | 索引 sitemap への分割、または生成の事前計算 |
| キーワード検索 | 公開求人が 5 万件を超える、または p95 が 300 ms を超えた時点 | PostgreSQL の全文検索（`tsvector` + GIN 索引）へ移行 |
| 一覧・詳細 | p95 が 200 ms を超えた時点 | 測り直して原因を特定する |

**いま直さない。**現時点の想定では、公開求人が 1 万件を超える運用は先である。
先回りで作り込むと、測っていない前提に基づく複雑さが増える。

## 再測定

データ量を変えたとき、または遅い SQL の記録（ADR 0049）が増えたときに測り直す。
測り直したら、この文書へ**行を足す**。前の値を消さない。増え方が読めなくなる。
