# アーキテクチャ原則

このプロジェクトの構造に関する判断基準を明文化する。
判断に迷った場合は、この文書の原則を優先する。

この文書は日本語版を正本とする。

## 1. 全体構成

### Rails によるモジュラーモノリスとする

単一の Rails アプリケーションとして開発し、業務境界は Ruby の名前空間で表現する。
初期段階でサービス分割を行わない。分割は、実際に分割しなければ解決できない問題が
計測結果として現れてから検討する。

業務モジュールは次の名前空間で表現する。

```text
Accounts
Organizations
JobPostings
CandidateProfiles
JobApplications
Hiring
Conversations
Notifications
Sourcing
Search
Integrations
Reporting
Operations
```

業務名前空間はトップレベルの Ruby 定数として定義する。
`RoleWeave::Application` は Rails 設定用の名前空間であり、
業務モジュールの共通親ではない。
Rails 標準の autoload 規約から外れる独自の root namespace 設定を追加しない。
ファイル配置は定数名と Rails 標準規約に従う。

```text
app/models/job_application.rb          -> JobApplication
app/services/job_applications/submit.rb -> JobApplications::Submit
app/services/hiring/advance_application.rb -> Hiring::AdvanceApplication
```

次は作らない。

```text
app/models/role_weave/job_application.rb -> RoleWeave::JobApplication
```

詳細は[開発言語・命名ポリシー](../development/language-policy.md)を参照する。

### Rails 標準の構造と命名規約を維持する

- `app/models`、`app/controllers`、`app/views`、`app/jobs` などを基本とする
- 定数とファイルパスは Rails の命名・autoload 規約に従う
- `app/services` は、明示的なユースケースクラスを置くための承認済み拡張ディレクトリとする
- `app/services` は、最初の具体的なユースケースが必要になった時点で追加する
- P0-T3 で空の `app/services` を先回りして作らない
- 将来用の空ディレクトリを追加しない
- 独自の autoload root 設定を追加しない
- `app/domains`、`app/use_cases`、`app/interactors` など、同じ責務を表す別ルートを並立させない

「独自の物理構成を増やさない」とは、承認済みの `app/services` を禁止する意味ではなく、
同じ責務のディレクトリを複数作らないこと、および使う予定のないディレクトリを
先回りして作らないことを指す。

Rails を知っている開発者が、追加の説明なしにコードの位置を推測できる状態を保つ。

### Rails 標準から大きく外れる独自基盤を作らない

Rails が提供する仕組み（Active Record、Active Job、Active Storage、Action Mailer など）
で足りる範囲は、それを使う。フレームワークを覆い隠す自作レイヤーを作らない。

## 2. データ

### PostgreSQL を正本データベースとする

業務上の真実は PostgreSQL に置く。

### 検索インデックスを正本にしない

検索用のデータ構造は、常に PostgreSQL から再構築できる派生物として扱う。
検索インデックスにしか存在しない情報を作らない。

### UI 上の状態をサーバー業務状態の正本にしない

クライアント側の状態は表示のための一時的なものとして扱う。
業務上の状態遷移はサーバー側で確定させる。

## 3. 境界と副作用

### 外部サービスはアダプター境界の外側に隔離する

メール送信、ファイル保存、CRM、カレンダー、Webhook などは、
アプリケーション側が定義したインターフェースの背後に置く。
業務モジュールから外部 SDK を直接参照しない。

### 外部 API をデータベーストランザクション内で呼ばない

外部通信はトランザクションの外で行う。
トランザクションを外部サービスの応答時間に依存させない。

### Active Record callback から外部サービスを呼ばない

callback には外部副作用を置かない。
保存の副作用として通信やメール送信が起きる状態を作らない。
副作用は、明示的なユースケース側で順序を制御する。

### 業務ルールを Controller に置かない

Controller は、入力の受け取り、認可の呼び出し、応答の組み立てに限定する。
判断ロジックは業務モジュール側に置く。

### メール送信失敗で応募処理を巻き戻さない

通知の失敗と業務処理の成否を分離する。
記録すべき業務上の事実は確定させ、通知は非同期に再試行可能な形で扱う。

### 業務モジュール同士の循環依存を禁止する

この制約はテストまたは静的検査で機械的に守る。

## 4. 依存関係の追加方針

### 全面的な抽象化を行わない

初期段階では、次のような全面適用を行わない。

- Repository パターンの全面導入
- イベントソーシングの全面導入
- すべての外部境界に対する先回りのインターフェース定義

抽象化は、複数の実装が実際に必要になった時点で追加する。

### 実装されていない将来機能の抽象化を先回りして追加しない

「後で必要になるかもしれない」という理由だけで拡張点を作らない。

### 実際の複雑性が確認されてから依存を追加する

依存を増やす判断は、推測ではなく計測または具体的な要求に基づいて行う。

### 初期段階で採用しないもの

- React
- Next.js
- GraphQL
- Redis
- OpenSearch
- Elasticsearch
- Kafka
- Kubernetes
- マイクロサービス
- 商用サービス固有の SDK への直接依存

Redis と OpenSearch は初期段階で必須にしない。
検索は PostgreSQL で実装し、OpenSearch の採用は実測結果を見て判断する。

## 5. ツールの適用範囲

### 開発タスク管理

開発タスクの定義と進捗は GitHub Issues と Pull Requests で管理する。
詳細は[開発工程](../development/workflow.md)を正本とする。
ツール固有の進捗台帳やイベント履歴を作業ツリーへ持ち込まない。

### `fsmxjs`

複雑なクライアント状態が実際に発生した場合だけ採用する。
採用する場合は ADR で判断の理由を記録する。
状態遷移が数個で済む画面に持ち込まない。

## 6. ゼロベース開発

### 既存実装の構造を移植しない

このプロジェクトは既存アプリケーションからの移植ではない。

- コードを移植しない
- データベース構造を再現しない
- ルーティングを再現しない
- 命名を引き継がない
- ディレクトリ構成を引き継がない

既存資料は、必要な機能を把握するための参考情報に限定する。
過去のシステムに由来する固有名詞をコードやドキュメントに持ち込まない。

## 7. 進め方

- 1 タスクにつき 1 つの確認可能な成果とする
- 1 タスクにつき 1 PR を原則とする
- コミットはレビュー可能な意味のある変更単位に分割できる
- WIP、fixup、意味のない修正コミットをマージ時に残さない
- main へのマージは原則 Squash merge とし、main 上では 1 タスク 1 コミットにまとめる
- 「認証を実装する」のような大きな単位でタスクを切らない
- 「同じ求職者が同じ求人へ二重応募できない」のような振る舞い単位で切る
- 各タスクには正の検証と負の検証の両方を用意する

### 横断品質要件を後続フェーズへ先送りしない

次の要件は、機能を追加するフェーズで同時に満たす。
「あとでセキュリティフェーズにまとめて対応する」という進め方を採らない。

- 認可
- 組織間分離
- 個人情報の最小化と、非公開を初期値とする設計
- 正の検証と負の検証
- 日本語と英語
- アクセシビリティ

正本は [`docs/project-principles.md`](../project-principles.md) と
[`docs/quality/cross-cutting-requirements.md`](../quality/cross-cutting-requirements.md) に置く。

P10 Privacy, Security and Operations は、これらの初回実装フェーズではない。
V1 全体に対する統合検証と、不足の是正を行うフェーズである。
候補者プロフィール、履歴書、応募時点のスナップショットは P6 と P7 で実装するため、
その安全性は P10 を待たずに、それぞれのフェーズで確定させる。
