# 開発の原則

計画と実装の判断に迷ったときは、この文書を優先する。
この文書は日本語版を正本とする。

詳細を別に持つものは次のとおり。ここには二重定義しない。

| 主題 | 正本 |
| --- | --- |
| 日本語と英語の使い分け、命名 | [`development/language-policy.md`](development/language-policy.md) |
| Issue・PR・検証の進め方 | [`development/workflow.md`](development/workflow.md) |
| 個別の設計判断 | [`decisions/`](decisions/)（ADR） |

## 1. 正本を 1 つにする

- 業務上の真実は PostgreSQL に置く。
  検索インデックスもクライアントの状態も、そこから再構築できる派生物として扱う
- 検索インデックスにしか存在しない情報を作らない
- 画面の状態を業務状態の正本にしない。状態遷移はサーバー側で確定させる
- 同じ判定を複数の経路へ書かない。書き忘れた経路が、そのまま入口になる。
  判定の置き場所は[アーキテクチャの概要](architecture/overview.md)に一覧がある

## 2. Rails 標準から外れない

- Rails が提供する仕組み（Active Record、Active Job、Active Storage、Action Mailer）
  で足りる範囲は、それを使う。フレームワークを覆い隠す自作レイヤーを作らない
- 単一の Rails アプリケーションとして開発し、業務境界は Ruby の名前空間で表現する。
  サービス分割は、分割しなければ解決できない問題が計測結果として現れてから検討する
- 定数とファイルパスは Rails の autoload 規約に従う。独自の autoload root を追加しない
- `app/services` は、明示的なユースケースクラスを置くための承認済みの拡張とする。
  最初の具体的なユースケースが必要になるまで作らない
- `app/domains`、`app/use_cases`、`app/interactors` のように、
  同じ責務を表すディレクトリを並立させない
- 使う予定のないディレクトリを先回りして作らない

Rails を知っている開発者が、追加の説明なしにコードの位置を推測できる状態を保つ。

## 3. 副作用を業務コードへ埋め込まない

- メール送信、ファイル保存、CRM、カレンダー、Webhook は、
  アプリケーション側が定義したインターフェースの背後に置く。
  業務モジュールから外部 SDK を直接参照しない
- 外部 API をデータベーストランザクションの中で呼ばない。
  トランザクションを外部サービスの応答時間に依存させない
- Active Record callback から外部通信を起こさない。
  副作用の順序は、明示的なユースケース側で制御する
- Controller は入力の受け取り、認可の呼び出し、応答の組み立てに限定する。
  判断ロジックを Controller へ置かない
- 通知の失敗で業務処理を巻き戻さない。
  記録すべき事実は確定させ、通知は非同期に再試行可能な形で扱う
- 業務モジュール同士の循環依存を禁止する。テストまたは静的検査で機械的に守る

## 4. 先回りして作らない

- 抽象化は、複数の実装が実際に必要になった時点で追加する。
  Repository パターン、イベントソーシング、全外部境界へのインターフェース定義を
  先に全面適用しない
- 「後で必要になるかもしれない」だけを理由に拡張点を作らない
- 依存を増やす判断は、推測ではなく計測または具体的な要求に基づく

初期段階で採用しないものは次のとおり。

React / Next.js / GraphQL / Redis / OpenSearch / Elasticsearch / Kafka /
Kubernetes / マイクロサービス / 商用サービス固有の SDK への直接依存

検索は PostgreSQL で実装する。OpenSearch の採用は実測結果を見て判断する。

## 5. 横断品質要件を先送りしない

次の 6 つは、機能を追加するのと同じ変更で満たす。
「あとでセキュリティ対応としてまとめて直す」という進め方を採らない。

| 要件 | 内容 |
| --- | --- |
| 認可 | 追加したデータと操作の認可を、同じ変更で実装する |
| 組織間分離 | 他組織から参照・変更できないことを、正の検証と負の検証で保証する |
| 個人情報 | 収集目的、公開範囲、保持、削除または匿名化を決める。**非公開を初期値とする** |
| 多言語 | 利用者向け文字列は日本語と英語を同時に実装する |
| アクセシビリティ | セマンティクス、ラベル、キーボード操作を同時に検証する |
| 検証 | 各タスクに正の検証と負の検証を設ける |

満たしている点と満たしていない点は[横断品質要件の検証状況](quality/verification-status.md)に書く。

## 6. コードの書き方

- コードコメント、テストの説明、コミット本文、PR は日本語。
  クラス名、メソッド名、変数名、ファイル名、DB、URL、i18n キーは自然な英語
- 処理内容を日本語で言い換えるだけのコメントを書かない。
  設計理由、制約、壊れやすい箇所、一見不自然な実装の必要性を説明するときに書く
- フォーマッターと Linter の出力を、手作業の好みより優先する。
  整形結果に不満があるときは、個別に書き換えず設定側を変更する
- 整形だけの変更を、振る舞いを変える変更と同じコミットへ混ぜない

## 7. タスクを振る舞いの単位で切る

- 1 タスクにつき 1 つの確認可能な成果とし、1 PR にまとめる
- 「認証を実装する」のような大きな単位で切らない。
  「同じ求職者が同じ求人へ二重応募できない」のような振る舞い単位で切る
- 正の検証と負の検証の両方を用意する。
  「できること」だけでなく「できてはいけないこと」ができないことを確認する
- 実行していない検証を成功として報告しない
- 完了条件は決定論的に検証できるものにする

## 8. ゼロベース開発

このプロジェクトは既存アプリケーションからの移植ではない。
コード、データベース構造、ルーティング、命名、ディレクトリ構成を引き継がない。
既存資料は、必要な機能を把握するための参考情報に限定する。
過去のシステムに由来する固有名詞を、コードにも文書にも持ち込まない。
